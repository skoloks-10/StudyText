## 프로세스와 스레드 기본 개념

### 프로세스 (Process)

### 정의

프로세스는 실행 중인 프로그램을 의미합니다. 프로그램이 메모리에 적재되어 CPU 자원을 할당받아 실행되는 상태를 말합니다.

### 프로세스의 구조

| 구성 요소                | 설명                         | 특징                                       |
| ------------------------ | ---------------------------- | ------------------------------------------ |
| **코드 영역**(Code/Text) | 실행 가능한 기계어 코드 저장 | 읽기 전용, 프로그램 실행 명령어 포함       |
| **데이터 영역**(Data)    | 전역 변수, 정적 변수 저장    | 프로그램 시작시 할당, 종료시 해제          |
| **힙 영역**(Heap)        | 동적 할당 메모리             | 프로그래머가 직접 관리, 런타임에 크기 결정 |
| **스택 영역**(Stack)     | 지역 변수, 함수 호출 정보    | 함수 호출/종료시 자동 할당/해제, LIFO 구조 |

### 프로세스의 특징

- **독립적인 메모리 공간** : 각 프로세스는 독립된 코드, 데이터, 힙, 스택 영역 보유
- **프로세스 ID (PID)** : 운영체제가 각 프로세스에 부여하는 고유 식별자
- **자원 소유** : 메모리, 파일, 입출력 장치 등 독립적인 시스템 자원 보유

### 스레드 (Thread)

### 정의

스레드는 프로세스 내에서 실행되는 실행 흐름의 단위입니다. 하나의 프로세스는 여러 개의 스레드를 가질 수 있습니다.

### 스레드의 구조

| 구성 요소           | 설명                      | 공유 여부 |
| ------------------- | ------------------------- | --------- |
| **프로그램 카운터** | 다음 실행할 명령어 위치   | 독립      |
| **레지스터**        | CPU 레지스터 값           | 독립      |
| **스택**            | 함수 호출 정보, 지역 변수 | 독립      |
| **코드 영역**       | 실행 코드                 | 공유      |
| **데이터 영역**     | 전역 변수                 | 공유      |
| **힙 영역**         | 동적 할당 메모리          | 공유      |

### 스레드의 특징

- **경량 프로세스** : 프로세스보다 생성/종료/전환 비용이 적음
- **자원 공유** : 같은 프로세스 내 스레드들은 코드, 데이터, 힙 영역 공유
- **독립적 실행 흐름** : 각 스레드는 독립적인 스택과 레지스터 보유

## 멀티프로세스와 멀티스레드

### 멀티프로세스 (Multi-Process)

### 개념

여러 개의 프로세스를 동시에 실행하여 작업을 처리하는 방식입니다.

### 장점과 단점

| 구분     | 내용                                                     |
| -------- | -------------------------------------------------------- |
| **장점** | - 안정성: 한 프로세스의 오류가 다른 프로세스에 영향 없음 |

- 독립성: 각 프로세스가 독립적인 메모리 공간 사용 |
  | **단점** | - 높은 오버헤드: 프로세스 생성/전환 비용이 큼
- 통신 복잡성: 프로세스 간 통신(IPC) 필요 |

### 사용 시나리오

```
상황: 웹 브라우저에서 여러 탭 실행
- 각 탭이 별도의 프로세스로 실행
- 한 탭의 크래시가 다른 탭에 영향 없음
- 보안과 안정성이 중요한 경우 적합

```

### 멀티스레드 (Multi-Thread)

### 개념

하나의 프로세스 내에서 여러 개의 스레드가 동시에 실행되어 작업을 처리하는 방식입니다.

### 장점과 단점

| 구분     | 내용                            |
| -------- | ------------------------------- |
| **장점** | - 경량성: 생성/전환 비용이 적음 |

- 자원 공유: 메모리를 효율적으로 사용
- 빠른 통신: 같은 메모리 공간 사용으로 통신 용이 |
  | **단점** | - 동기화 문제: 공유 자원 접근시 경쟁 상태(race condition) 발생 가능
- 안정성: 한 스레드의 오류가 전체 프로세스에 영향 |

### 사용 시나리오

```
상황: 게임 프로그램
- UI 렌더링 스레드
- 물리 연산 스레드
- 네트워크 통신 스레드
- 빠른 응답성과 효율적인 자원 사용이 필요한 경우 적합

```

## 프로세스 간 통신 (IPC)

### IPC의 필요성

독립적인 메모리 공간을 가진 프로세스들이 데이터를 주고받고 협력하기 위해서는 **IPC(Inter-Process Communication)** 메커니즘이 필요합니다.

### 주요 IPC 방법

| 방법                            | 설명                                    | 특징        | 사용 예시 |
| ------------------------------- | --------------------------------------- | ----------- | --------- |
| **공유 메모리** (Shared Memory) | 여러 프로세스가 접근 가능한 메모리 영역 | - 빠른 속도 |           |

- 동기화 필요
- 대용량 데이터 전송에 유리 | 프로세스 A와 B가 큰 데이터셋 공유 |
  | **메시지 전달** (Message Passing) | 운영체제를 통해 메시지 송수신 | - 안전성 높음
- 속도는 상대적으로 느림
- 작은 데이터 전송에 적합 | 클라이언트-서버 통신 |
  | **파이프** (Pipe) | 한쪽 방향으로만 데이터 흐름 | - 단방향 통신
- 부모-자식 프로세스 간 주로 사용 | 셸 명령어 파이프라인``<br>```ls |
  | **소켓** (Socket) | 네트워크를 통한 프로세스 간 통신 | - 원격 통신 가능
- 양방향 통신
- TCP/UDP 프로토콜 사용 | 웹 서버-클라이언트 통신 |

### JavaScript에서의 IPC 예시

### Node.js - Child Process 통신

```jsx
// 사용 목적: 자식 프로세스 생성 및 통신
// 사용 시기: 무거운 작업을 별도 프로세스로 분리할 때

const { fork } = require("child_process");

// 부모 프로세스
const child = fork("child.js");

// 자식에게 메시지 전송
child.send({ type: "calculate", data: [1, 2, 3, 4, 5] });

// 자식으로부터 메시지 수신
child.on("message", (msg) => {
  console.log("결과:", msg.result);
});

// child.js (자식 프로세스)
process.on("message", (msg) => {
  if (msg.type === "calculate") {
    const sum = msg.data.reduce((a, b) => a + b, 0);
    process.send({ result: sum });
  }
});
```

### Web Workers - 브라우저에서의 멀티스레드

```jsx
// 사용 목적: 메인 스레드를 블로킹하지 않고 무거운 연산 수행
// 사용 시기: 복잡한 계산, 이미지 처리 등

// main.js

};
```

## CPU 스케줄링

### CPU 스케줄링 개요

### 정의

CPU 스케줄링은 여러 프로세스가 CPU 자원을 효율적으로 사용할 수 있도록 CPU를 할당하는 방법을 결정하는 것입니다.

### 스케줄링의 필요성

- 운영체제가 여러 프로세스를 동시에 실행해야 함
- 제한된 CPU 자원을 효율적으로 분배
- 시스템 성능과 응답 시간 최적화

### CPU 스케줄링 큐

### 큐의 종류

| 큐 종류         | 역할                                   | 프로세스 상태 |
| --------------- | -------------------------------------- | ------------- |
| **준비 큐**     |                                        |               |
| (Ready Queue)   | CPU 할당을 기다리는 프로세스 저장      | Ready 상태    |
| **대기 큐**     |                                        |               |
| (Waiting Queue) | I/O 작업 완료를 기다리는 프로세스 저장 | Waiting 상태  |
| **실행**        |                                        |               |
| (Running)       | 현재 CPU를 사용중인 프로세스           | Running 상태  |

### 프로세스 상태 전이

```
생성 (New)
  ↓
준비 (Ready) ←――――――――┐
  ↓                    │
실행 (Running) ―――――――┤
  ↓                    │
대기 (Waiting) ―――――――┘
  ↓
종료 (Terminated)

```

### 스케줄링 알고리즘

### 선점형 vs 비선점형

| 구분     | 선점형 (Preemptive)                    | 비선점형 (Non-Preemptive)                    |
| -------- | -------------------------------------- | -------------------------------------------- |
| **정의** | CPU를 빼앗아 다른 프로세스에 할당 가능 | 프로세스가 자발적으로 CPU 반납할 때까지 대기 |
| **장점** | - 응답성 좋음                          |                                              |

- 우선순위 높은 작업 즉시 처리 | - 문맥 교환 오버헤드 적음
- 구현 단순 |
  | **단점** | - 문맥 교환 오버헤드
- 복잡한 구현 | - 응답 시간 예측 어려움
- 긴 작업이 CPU 독점 가능 |

### 주요 스케줄링 알고리즘

| 알고리즘                  | 방식                      | 선점/비선점 | 특징        | JavaScript 시뮬레이션 |
| ------------------------- | ------------------------- | ----------- | ----------- | --------------------- |
| **FCFS**                  |                           |             |             |                       |
| (First Come First Served) | 먼저 도착한 순서대로 처리 | 비선점형    | - 구현 간단 |                       |

- 긴 작업이 먼저 오면 대기 시간 증가 | `queue.shift()` |
  | **SJF**
  (Shortest Job First) | 실행 시간이 짧은 작업 우선 | 비선점형 | - 평균 대기 시간 최소
- 실행 시간 예측 필요 | `queue.sort((a,b) => a.time - b.time)` |
  | **Round Robin** | 시간 할당량(타임 슬라이스)만큼 순환 | 선점형 | - 공정성 보장
- 응답 시간 좋음
- 문맥 교환 빈번 | 순환 큐 구현 |
  | **Priority** | 우선순위가 높은 작업 먼저 | 선점/비선점형 모두 가능 | - 중요한 작업 빠른 처리
- 기아(starvation) 문제 발생 가능 | `queue.sort((a,b) => b.priority - a.priority)` |
  | **Multilevel Queue** | 여러 큐로 분리, 각 큐마다 다른 알고리즘 | 선점형 | - 프로세스 특성에 맞는 처리
- 복잡한 구현 | 다중 큐 배열 |

### JavaScript 스케줄링 시뮬레이션 예제

### Round Robin 스케줄링 구현

```jsx
// 사용 목적: 모든 프로세스에 공정하게 CPU 시간 분배
// 사용 시기: 대화형 시스템, 시분할 시스템

class Process {
  constructor(id, burstTime) {
    this.id = id;
    this.burstTime = burstTime; // 총 실행 시간
    this.remainingTime = burstTime; // 남은 실행 시간
  }
}

function roundRobinScheduling(processes, timeQuantum) {
  const queue = [...processes];
  const timeline = [];
  let currentTime = 0;

  while (queue.length > 0) {
    const process = queue.shift();

    // 타임 슬라이스만큼 실행
    const executionTime = Math.min(timeQuantum, process.remainingTime);
    process.remainingTime -= executionTime;
    currentTime += executionTime;

    timeline.push({
      processId: process.id,
      startTime: currentTime - executionTime,
      endTime: currentTime,
    });

    // 작업이 완료되지 않았으면 큐의 맨 뒤로
    if (process.remainingTime > 0) {
      queue.push(process);
    }
  }

  return timeline;
}

// 사용 예시
const processes = [
  new Process("P1", 10),
  new Process("P2", 5),
  new Process("P3", 8),
];

const result = roundRobinScheduling(processes, 3);
console.log("스케줄링 결과:", result);
```

### Priority 스케줄링 구현

```jsx
// 사용 목적: 중요한 작업에 우선순위 부여
// 사용 시기: 실시간 시스템, 우선순위가 명확한 환경

class PriorityProcess {
  constructor(id, burstTime, priority) {
    this.id = id;
    this.burstTime = burstTime;
    this.priority = priority; // 숫자가 작을수록 높은 우선순위
  }
}

function priorityScheduling(processes) {
  // 우선순위로 정렬 (낮은 숫자 = 높은 우선순위)
  const sorted = processes.sort((a, b) => a.priority - b.priority);

  let currentTime = 0;
  const timeline = [];

  for (const process of sorted) {
    timeline.push({
      processId: process.id,
      priority: process.priority,
      startTime: currentTime,
      endTime: currentTime + process.burstTime,
    });
    currentTime += process.burstTime;
  }

  return timeline;
}

// 사용 예시
const priorityProcesses = [
  new PriorityProcess("P1", 10, 3),
  new PriorityProcess("P2", 5, 1), // 가장 높은 우선순위
  new PriorityProcess("P3", 8, 2),
];

const result = priorityScheduling(priorityProcesses);
console.log("우선순위 스케줄링:", result);
```

## 스케줄링 큐와 알고리즘

### 스케줄링 큐의 구조

### 단일 스레드 프로세스 vs 멀티 스레드 프로세스

| 항목          | 단일 스레드                   | 멀티 스레드                               |
| ------------- | ----------------------------- | ----------------------------------------- |
| **구조**      | 프로세스 내 하나의 실행 흐름  | 프로세스 내 여러 실행 흐름                |
| **자원 공유** | 모든 자원 독립적              | 코드, 데이터, 힙 공유                     |
| **스케줄링**  | 프로세스 단위 스케줄링        | 스레드 단위 스케줄링 가능                 |
| **예시**      | `hello.txt`파일 처리 프로그램 | 웹 브라우저 (UI, 네트워크, 렌더링 스레드) |

### 프로세스 우선순위

### 우선순위 관리

운영체제는 프로세스에 우선순위를 부여하여 CPU 자원 할당 순서를 결정합니다.

| 우선순위 유형     | 설명                                  | 특징        |
| ----------------- | ------------------------------------- | ----------- |
| **정적 우선순위** | 프로세스 생성 시 결정되어 변하지 않음 | - 구현 간단 |

- 유연성 낮음 |
  | **동적 우선순위** | 실행 중 우선순위 변경 가능 | - 유연한 스케줄링
- 에이징(aging) 기법으로 기아 방지 |

### 우선순위 문제: 기아 현상 (Starvation)

```
문제: 낮은 우선순위 프로세스가 무한정 대기
해결책: 에이징(Aging) 기법
- 대기 시간이 길어질수록 우선순위 점진적 증가
- 결국 모든 프로세스가 실행 기회 획득

```

### JavaScript에서의 우선순위 큐 구현

```jsx
// 사용 목적: 우선순위에 따른 작업 처리
// 사용 시기: 이벤트 처리, 작업 스케줄링

class PriorityQueue {
  constructor() {
    this.items = [];
  }

  // 우선순위에 따라 삽입
  enqueue(item, priority) {
    const element = { item, priority };
    let added = false;

    for (let i = 0; i < this.items.length; i++) {
      if (element.priority < this.items[i].priority) {
        this.items.splice(i, 0, element);
        added = true;
        break;
      }
    }

    if (!added) {
      this.items.push(element);
    }
  }

  dequeue() {
    return this.items.shift();
  }

  isEmpty() {
    return this.items.length === 0;
  }
}

// 사용 예시
const pq = new PriorityQueue();
pq.enqueue("긴급 작업", 1);
pq.enqueue("일반 작업", 3);
pq.enqueue("중요 작업", 2);

while (!pq.isEmpty()) {
  const task = pq.dequeue();
  console.log(`처리: ${task.item} (우선순위: ${task.priority})`);
}
```

### 문맥 교환 (Context Switch)

### 개념

CPU가 한 프로세스에서 다른 프로세스로 전환될 때, 현재 프로세스의 상태를 저장하고 새 프로세스의 상태를 복원하는 과정입니다.

### 문맥 교환 과정

| 단계                   | 작업 내용                                                   |
| ---------------------- | ----------------------------------------------------------- |
| 1.**상태 저장**        | 현재 프로세스의 레지스터, 프로그램 카운터, 스택 포인터 저장 |
| 2.**PCB 업데이트**     | Process Control Block에 상태 정보 기록                      |
| 3.**새 프로세스 선택** | 스케줄러가 다음 실행할 프로세스 결정                        |
| 4.**상태 복원**        | 새 프로세스의 PCB에서 상태 정보 로드                        |
| 5.**실행 재개**        | 새 프로세스 실행 시작                                       |

### 문맥 교환 비용

- **직접 비용** : 레지스터 저장/복원 시간
- **간접 비용** : 캐시, TLB 무효화로 인한 성능 저하
- **최적화** : 문맥 교환 빈도를 줄이는 스케줄링 알고리즘 선택

## 핵심 요약

### 프로세스 vs 스레드

- **프로세스** : 독립적 메모리 공간, 높은 안정성, 큰 오버헤드
- **스레드** : 공유 메모리, 경량, 빠른 통신, 동기화 필요

### IPC 방법

- **공유 메모리** : 빠른 대용량 데이터 전송
- **메시지 전달** : 안전한 소량 데이터 통신
- **파이프** : 단방향 부모-자식 통신
- **소켓** : 네트워크 기반 원격 통신

### CPU 스케줄링 핵심

- **목적** : 제한된 CPU 자원의 효율적 분배
- **선점형** : 응답성 우선, 문맥 교환 빈번
- **비선점형** : 오버헤드 최소, 긴 작업 대기 문제

### 주요 알고리즘 선택 기준

- **FCFS** : 단순 구현, 배치 작업
- **Round Robin** : 공정성, 대화형 시스템
- **Priority** : 중요도 기반, 실시간 시스템
- **SJF** : 평균 대기 시간 최소화

## 복습 퀴즈

### Q1. 프로세스와 스레드의 차이점에 대한 설명으로 옳은 것은?

**① 프로세스는 코드 영역을 공유하지만, 스레드는 각자 독립적인 코드 영역을 가진다.**

② 스레드는 같은 프로세스 내에서 힙 영역을 공유한다.

③ 프로세스 간 통신은 스레드 간 통신보다 항상 빠르다.

④ 스레드는 독립적인 PID를 가진다.

**정답: ②**

**해설** :
같은 프로세스 내의 스레드들은 코드, 데이터, 힙 영역을 공유합니다. 각 스레드는 독립적인 스택과 레지스터만 가지고 있어 경량화되어 있습니다.

- ①은 반대입니다. 스레드가 코드 영역을 공유합니다.
- ③은 틀렸습니다. 스레드 간 통신이 메모리 공유로 더 빠릅니다.
- ④는 틀렸습니다. PID는 프로세스 단위로 부여되며, 스레드는 TID(Thread ID)를 가집니다.

### Q2. IPC(Inter-Process Communication) 방법 중 대용량 데이터를 가장 빠르게 전송할 수 있는 방법은?

① 메시지 전달 (Message Passing)

**② 공유 메모리 (Shared Memory)**

③ 파이프 (Pipe)

④ 소켓 (Socket)

**정답: ②**

**해설** :
공유 메모리는 여러 프로세스가 동일한 메모리 영역에 직접 접근할 수 있어 운영체제의 개입 없이 데이터를 교환할 수 있습니다. 이는 대용량 데이터 전송에 가장 효율적입니다.

- ①, ③, ④는 모두 운영체제의 중재나 네트워크를 거쳐야 하므로 공유 메모리보다 느립니다.
- 단, 공유 메모리는 동기화 문제를 해결해야 하는 단점이 있습니다.

---

### Q3. Round Robin 스케줄링 알고리즘에 대한 설명으로 틀린 것은?

① 선점형 스케줄링 알고리즘이다.

② 각 프로세스에 동일한 시간 할당량(타임 슬라이스)을 부여한다.

**③ 평균 대기 시간이 가장 짧은 스케줄링 알고리즘이다.**

④ 응답 시간이 예측 가능하고 공정성을 보장한다.

**정답: ③**

**해설** :
평균 대기 시간이 가장 짧은 알고리즘은 SJF(Shortest Job First)입니다. Round Robin은 공정성과 응답성에 초점을 맞춘 알고리즘으로, 모든 프로세스에 균등한 CPU 시간을 제공합니다.

- ①, ②, ④는 Round Robin의 올바른 특징입니다.
- Round Robin은 대화형 시스템에서 모든 사용자에게 빠른 응답을 제공하기 위해 설계되었습니다.

### Q4. 문맥 교환(Context Switch)에 대한 설명으로 옳은 것은?

① 문맥 교환은 프로세스의 종료 시에만 발생한다.

② 문맥 교환이 빈번할수록 시스템 성능이 향상된다.

**③ 문맥 교환 시 현재 프로세스의 레지스터 값을 PCB에 저장한다.**

④ 스레드 간 문맥 교환은 프로세스 간 문맥 교환보다 항상 비용이 크다.

**정답: ③**

**해설** :
문맥 교환 시 CPU는 현재 실행 중인 프로세스의 상태(레지스터, 프로그램 카운터등) 를 PCB(Process Control Block)에 저장하고, 다음 실행할 프로세스의 PCB에서 상태를 복원합니다.

- ①은 틀렸습니다. 문맥 교환은 스케줄링 시, 인터럽트 발생 시 등 다양한 경우에 일어납니다.
- ②는 틀렸습니다. 문맥 교환은 오버헤드를 발생시켜 과도하면 성능 저하를 일으킵니다.
- ④는 틀렸습니다. 스레드 간 문맥 교환이 메모리를 공유하므로 비용이 더 적습니다.

---

### Q5. CPU 스케줄링에서 기아(Starvation) 현상을 해결할 수 있는 방법은?

① FCFS 알고리즘 사용

② 타임 슬라이스를 무한대로 설정

**③ 에이징(Aging) 기법 적용**

④ 항상 가장 짧은 작업을 먼저 실행

**정답: ③**

**해설** :
에이징(Aging) 기법은 대기 시간이 길어질수록 프로세스의 우선순위를 점진적으로 높여주는 방법입니다. 이를 통해 낮은 우선순위 프로세스도 결국 실행될 기회를 얻을 수 있어 기아 현상을 방지합니다.

- ①은 기아 문제와 무관하며, 긴 작업으로 인한 대기 시간 증가 문제가 있습니다.
- ②는 실행 중인 프로세스가 CPU를 독점하게 되어 오히려 기아를 악화시킵니다.
- ④(SJF)는 긴 작업이 계속 밀려나 기아 현상을 일으킬 수 있습니다.
