## 1. `git log` — 히스토리 탐색

### 언제 쓰는가?

- 프로젝트에서 "언제, 누가, 무엇을 바꿨는지" 추적할 때
- 브랜치 간 커밋 차이를 확인할 때
- 특정 파일이나 기능이 언제 추가됐는지 찾을 때

---

### 기본 → 심화 흐름

```bash
# 기본: 전체 커밋 이력
git log

# 한 줄 요약 (빠른 훑기)
git log --oneline

# 브랜치 흐름을 그래프로 시각화
git log --graph --oneline --all
```

---

### 자주 쓰는 옵션 정리

| 옵션 | 목적 | 언제 쓰는가 |
|------|------|------------|
| `--oneline` | 커밋을 한 줄로 요약 | 빠른 히스토리 확인 |
| `--graph` | 브랜치 분기를 선으로 표현 | 병합 흐름 파악 |
| `--all` | 모든 브랜치 포함 | 다른 브랜치도 함께 확인 |
| `--decorate` | 브랜치·태그 이름 표시 | 커밋과 브랜치 관계 파악 |
| `-p` | 실제 코드 변경(diff) 포함 | 뭘 바꿨는지 내용까지 확인 |
| `--stat` | 파일별 변경 줄 수 요약 | 변경 규모를 빠르게 파악 |
| `-n 숫자` | 최근 N개 커밋만 출력 | 최근 작업만 볼 때 |

---

### 🎯 검색/필터 옵션

```bash
# 특정 작성자의 커밋만
git log --author="홍길동"

# 날짜 범위 지정
git log --since="2024-01-01" --until="2024-12-31"

# 커밋 메시지로 검색
git log --grep="버그 수정"

# 특정 문자열이 추가/삭제된 커밋 찾기
git log -S "함수명"

# 특정 파일의 변경 이력만
git log 파일명

# 파일의 변경 이유까지 (내용 포함)
git log -p 파일명
```

---

### ⚠️ 헷갈리는 포인트: `..` vs `...`

```bash
# A에 없고 B에만 있는 커밋
git log A..B

# 두 브랜치가 갈라진 이후 양쪽 모두의 커밋
git log A...B
```

> 💡 점 2개(`..`)는 "B가 A보다 앞선 커밋", 점 3개(`...`)는 "공통 조상 이후 양쪽 모두"

## 2. `git diff` — 변경 내용 비교

### 언제 쓰는가?

- 커밋 전 내가 바꾼 내용을 최종 확인할 때
- 스테이징된 내용과 실제 파일 차이를 볼 때
- 두 커밋 혹은 브랜치 간 차이를 비교할 때

---

### 상황별 사용법

```bash
# 워킹 디렉토리 변경사항 (아직 add 안 한 것)
git diff

# 스테이지된 변경사항 (add는 했지만 commit 안 한 것)
git diff --staged

# 특정 두 커밋 간 비교
git diff (커밋해시1) (커밋해시2)

# 브랜치 간 비교
git diff (브랜치1) (브랜치2)
```

> 💡 현재 커밋과 이전 커밋을 비교하려면 이전 커밋 해시만 써도 됩니다: `git diff HEAD~1`

---

### 출력 방식 변경 옵션

```bash
# 파일 이름만 확인 (내용 없이)
git diff --name-only

# 파일별 변경 줄 수 통계만
git diff --stat

# 단어 단위 변경 강조 (줄 전체가 아닌 단어만)
git diff --color-words

# 공백 차이 무시 (코드 내용만 비교)
git diff -w
```

---

### ⚠️ 헷갈리는 포인트

- `git diff` — add 전 변경사항만 보임
- `git diff --staged` — add 후 commit 전 변경사항만 보임
- 둘 다 보려면 따로따로 실행해야 함

## 3. `git blame` — 작성자 추적

### 언제 쓰는가?

- 특정 코드 줄이 누가 작성했는지 확인할 때
- "이 코드 왜 이렇게 됐지?" 하고 히스토리를 찾을 때
- 코드 리뷰나 버그 추적 시

---

### 사용법

```bash
# 파일 전체의 줄별 작성자 확인
git blame 파일명

# 사용자명 대신 이메일 표시
git blame -e 파일명

# 특정 줄 범위만 확인
git blame -L 10,20 파일명

# 10번 줄부터 5줄만 확인
git blame -L 10,+5 파일명
```

---

### 💡 실무 팁

> VS Code에서 **GitLens** 확장 프로그램을 사용하면 코드 옆에 바로 작성자와 커밋 정보가 표시됩니다. 터미널 명령보다 훨씬 편리하므로 꼭 설치해보세요!

## 4. `git bisect` — 버그 시점 이진 탐색

### 언제 쓰는가?

- "예전엔 됐는데 지금은 안 돼" 상황에서 어느 커밋부터 문제가 생겼는지 찾을 때
- 커밋이 많아서 하나씩 확인하기 어려울 때 (이진 탐색으로 빠르게 좁힘)

---

### 작동 원리

이진 탐색(Binary Search)과 동일한 원리입니다. "정상"과 "오류" 사이의 중간 커밋을 계속 확인하며 범위를 절반씩 줄여나갑니다.

```
정상 커밋 ──────────────── 오류 커밋
          ↑ 중간 확인
          good 또는 bad 표시
          → 범위 절반으로 줄임 → 반복
```

---

### 사용 순서

```bash
# 1단계: 이진 탐색 시작
git bisect start

# 2단계: 현재(오류 있음) 표시
git bisect bad

# 3단계: 정상이었던 커밋으로 이동
git checkout (정상 커밋 해시)

# 4단계: 정상임을 표시
git bisect good

# ↓ Git이 중간 커밋으로 자동 이동

# 5단계: 테스트 후 good 또는 bad 반복 표시
git bisect good   # 또는
git bisect bad

# → 원인 커밋을 찾을 때까지 반복

# 6단계: 탐색 종료 (원래 상태로 복귀)
git bisect reset
```

---

### ⚠️ 헷갈리는 포인트

- `bisect bad`는 항상 **현재(오류 있는)** 상태에 먼저 씁니다.
- `bisect good`은 **정상이었던 과거** 커밋에 씁니다.
- 탐색이 끝나면 반드시 `bisect reset`으로 종료해야 합니다. 잊으면 HEAD가 떠 있는 상태로 남습니다.

---

## ⚡ 핵심 요약

| 명령어 | 핵심 목적 | 가장 자주 쓰는 형태 |
|--------|-----------|-------------------|
| `git log` | 커밋 히스토리 탐색 | `git log --oneline --graph --all` |
| `git diff` | 변경 내용 비교 | `git diff --staged` |
| `git blame` | 줄별 작성자 확인 | `git blame -L 시작,끝 파일명` |
| `git bisect` | 버그 발생 시점 이진 탐색 | `start → bad → good → 반복 → reset` |

> 💡 실무에서 가장 많이 쓰이는 조합: `git log --oneline --graph --all` + `git diff --staged` + GitLens

## 📝 복습 퀴즈

### Q1. 모든 브랜치의 커밋 흐름을 한눈에 그래프로 보고 싶을 때 올바른 명령어는?

1. `git log --graph`
2. `git log --all --oneline`
3. `git log --graph --oneline --all`
4. `git log --decorate --all`
5. `git log --stat --all`

정답: 3번

해설: `--graph`는 브랜치 관계를 선으로 표현하고, `--oneline`은 한 줄 요약, `--all`은 모든 브랜치를 포함합니다. 세 옵션을 함께 써야 가장 넓게 한눈에 확인할 수 있습니다.

---

### Q2. `git diff`와 `git diff --staged`의 차이로 올바른 것은?

1. `git diff`는 커밋 간 비교, `git diff --staged`는 브랜치 간 비교이다.
2. `git diff`는 add 전 변경사항, `git diff --staged`는 add 후 commit 전 변경사항을 보여준다.
3. `git diff --staged`는 마지막 커밋과 현재 워킹 디렉토리를 비교한다.
4. 두 명령어는 동일한 결과를 출력한다.
5. `git diff`는 현재 브랜치만, `git diff --staged`는 모든 브랜치의 변경사항을 보여준다.

정답: 2번

해설: `git diff`는 워킹 디렉토리(아직 `git add`하지 않은 변경사항)를 보여줍니다. `git diff --staged`는 스테이징 영역(이미 `git add`는 했지만 `git commit`은 하지 않은 상태)의 변경사항을 보여줍니다.

---

### Q3. `git log A..B`와 `git log A...B`의 차이를 올바르게 설명한 것은?

1. `A..B`는 A와 B 모두의 커밋, `A...B`는 A에만 있는 커밋이다.
2. `A..B`는 두 브랜치 전체 히스토리, `A...B`는 최근 커밋만 보여준다.
3. `A..B`는 A에 없고 B에만 있는 커밋, `A...B`는 공통 조상 이후 양쪽 모두의 커밋이다.
4. 점의 개수는 상관없고 동일한 결과를 출력한다.
5. `A...B`는 병합 커밋만 보여준다.

정답: 3번

해설: 점 2개(`..`)는 B에는 있지만 A에는 없는 커밋을 보여줍니다. 점 3개(`...`)는 두 브랜치가 공통 조상에서 갈라진 이후, 양쪽 브랜치 각각에서 새로 추가된 모든 커밋을 보여줍니다.

### Q4. `git bisect`를 사용하는 올바른 순서는?

1. `good → bad → start → reset`
2. `start → good → bad → reset`
3. `start → bad → good → (반복) → reset`
4. `bad → good → start → reset`
5. `start → reset → bad → good`

정답: 3번

해설: 먼저 `git bisect start`로 탐색을 시작하고, 현재 상태(오류 있음)를 `bad`로 표시합니다. 그 다음 정상이었던 과거 커밋으로 이동하여 `good`을 표시하면 Git이 자동으로 중간 커밋으로 이동합니다. 이후 `good` 또는 `bad`를 반복하여 범위를 좁히고, 원인을 찾으면 `reset`으로 종료합니다.

### Q5. 파일에서 특정 줄의 작성자를 확인하는 올바른 명령어는?

1. `git log --author 파일명`
2. `git diff -L 10,20 파일명`
3. `git blame -L 10,20 파일명`
4. `git log -L 10,20 파일명`
5. `git blame --stat 파일명`

정답: 3번

해설: `git blame`은 파일의 각 줄이 누가 언제 작성했는지 표시해주는 명령어입니다. `-L` 옵션으로 `시작줄,끝줄` 형식 또는 `시작줄,+줄수` 형식으로 범위를 지정할 수 있습니다. `git log -L`도 존재하지만, 줄별 작성자 확인은 `blame`이 전담합니다.
