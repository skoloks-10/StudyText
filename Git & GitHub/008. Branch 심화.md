# 🍒 Git 고급 명령어 & 브랜치 전략 복습 노트

> 📅 작성 목적: 빠른 재열람을 위한 핵심 정리본
> 📌 대상: Git 기본기를 익힌 후 고급 명령어를 학습 중인 분

---

## 1. 🍒 cherry-pick — 원하는 커밋만 쏙 가져오기

### 언제 쓰나?
- 다른 브랜치에 있는 **특정 커밋 하나만** 현재 브랜치로 가져오고 싶을 때
- 브랜치 전체를 merge하기는 부담스럽고, 딱 하나의 변경사항만 필요할 때

### 사용법
```bash
# 현재 브랜치(예: main)에서 실행
git cherry-pick <가져올 커밋의 해시>
```

### 자주 헷갈리는 포인트 ⚠️
- cherry-pick은 **복사**다. 원본 브랜치의 커밋이 사라지지 않는다.
- 커밋 해시는 `git log`로 확인할 수 있다. (앞 7자리만 써도 됨)
- 충돌(conflict)이 발생하면 직접 해결 후 `git cherry-pick --continue` 실행

## 2. 🌿 rebase --onto — 브랜치를 통째로 옮겨붙이기

### 언제 쓰나?
- A 브랜치에서 파생된 B 브랜치를, **전혀 다른 C 브랜치 위로 이동**시키고 싶을 때
- 잘못된 시작점에서 브랜치를 만들었을 때 교정용으로 사용

### 사용법
```bash
git rebase --onto <도착 브랜치> <출발 브랜치> <이동할 브랜치>
```

### 예시 시나리오
`fruit` 브랜치에서 파생된 `citrus`를 `main` 위로 이동할 때:

```bash
git rebase --onto main fruit citrus
# 이후 citrus로 fast-forward
git switch main
git merge citrus
```

### 자주 헷갈리는 포인트 ⚠️
- 인자 순서가 헷갈린다: `도착지` → `출발지(현재 붙어있는 곳)` → `옮길 브랜치` 순서
- 실수로 rebase를 했다면? `git reflog`로 이전 상태의 해시를 찾아 `git reset --hard <해시>`로 복구 가능

## 3. 📦 merge --squash — 여러 커밋을 하나로 압축해서 가져오기

### 언제 쓰나?
- 작업 브랜치의 지저분한 커밋 내역을 main에 남기기 싫을 때
- 여러 커밋을 **하나의 깔끔한 커밋으로 합쳐서** 메인 브랜치에 반영하고 싶을 때

### 사용법
```bash
# main 브랜치에서 실행
git merge --squash <대상 브랜치>

# 변경사항이 staged 상태로 대기 중이므로, 직접 커밋
git commit -m "작업 브랜치 내용 통합"
```

### 일반 merge vs merge --squash 비교

| 구분 | 일반 merge | merge --squash |
|------|-----------|----------------|
| 코드 결과 | 동일 | 동일 |
| 커밋 내역 | 두 브랜치가 이어붙여짐 | B의 커밋들이 1개로 압축되어 A에 추가 |
| 브랜치 연결 | 유지됨 (merge commit 생성) | 연결 없음 (독립된 커밋) |
| 사용 목적 | 브랜치 이력 보존 | 깔끔한 이력 관리 |

### 자주 헷갈리는 포인트 ⚠️
- `--squash` 후에는 반드시 `git commit`을 수동으로 해야 한다. 자동으로 커밋되지 않음!
- 실행 후 대상 브랜치는 삭제해도 무방 (이력이 main에 녹아들었기 때문)

## 4. 🌳 브랜치 전략 비교

> 팀의 규모, 배포 방식에 따라 알맞은 전략을 선택한다.

### Git Flow

- 명확한 역할 분리가 필요한 **대규모 프로젝트**에 적합
- 릴리즈 주기가 긴 프로덕트에 유리

| 브랜치 | 성격 | 역할 |
|--------|------|------|
| `main` | 영구 | 실제 배포된 최신 버전 |
| `develop` | 영구 | 다음 배포를 위한 통합 브랜치 |
| `feature` | 임시 | 기능 개발 (develop에서 생성 → develop으로 병합) |
| `release` | 임시 | 배포 직전 QA 및 버그 수정 |
| `hotfix` | 임시 | 운영 중 긴급 버그 수정 |

### GitHub Flow

- `main` 하나를 중심으로 돌아가는 **단순한 구조**
- 상시 배포(CD)가 갖춰진 웹 서비스에 최적
- Pull Request(PR) 기반 코드 리뷰 문화와 찰떡궁합

```
feature 브랜치 → PR 생성 → 리뷰 → main 병합 → 배포
```

### Trunk-based Development (TBD)

- 모든 개발자가 **매일 main 브랜치에 직접 병합**
- 충돌을 최소화하고 개발 속도를 극대화
- 자동화 테스트와 **Feature Flag** (기능 토글)가 필수 조건

### 전략 한눈에 비교

| 전략 | 브랜치 구조 | 핵심 가치 | 적합한 팀 |
|------|------------|----------|-----------|
| Git Flow | main, develop, feature, release, hotfix | 엄격한 관리 & 안정성 | 대규모, 긴 릴리즈 주기 |
| GitHub Flow | main + topic 브랜치 | 단순함 & 빠른 배포 | 중소규모, 상시 배포 |
| TBD | main (Trunk) 하나 | 지속적 통합 & 속도 | 고숙련 팀, 자동화 완비 |

---

## 📝 핵심 요약 (Quick Reference)

| 명령어 | 한 줄 요약 |
|--------|-----------|
| `git cherry-pick <hash>` | 다른 브랜치의 특정 커밋 하나만 복사해옴 |
| `git rebase --onto A B C` | C 브랜치를 B에서 떼어 A 위에 붙임 |
| `git merge --squash <branch>` | 브랜치의 여러 커밋을 1개로 압축해 staged 상태로 가져옴 |

> 🔑 공통 포인트: 세 명령어 모두 "코드 결과"는 같아 보여도, **커밋 히스토리가 달라진다**는 것이 핵심!

## 🧪 복습 퀴즈

### Q1. cherry-pick에 대한 설명으로 올바른 것은?

1. 다른 브랜치 전체를 현재 브랜치로 병합한다.
2. 특정 커밋을 현재 브랜치로 복사해온다.
3. 여러 커밋을 하나로 압축해서 가져온다.
4. 브랜치를 다른 시작점으로 이동시킨다.
5. 충돌이 발생하면 자동으로 해결된다.

정답: 2번

해설: cherry-pick은 특정 커밋(들)만 선택해 현재 브랜치로 "복사"하는 명령어다. 원본 브랜치의 커밋은 사라지지 않으며, 충돌 발생 시 수동 해결 후 --continue로 진행해야 한다.

---

### Q2. `git rebase --onto main fruit citrus` 명령의 의미로 올바른 것은?

1. main 브랜치를 fruit 브랜치 위로 이동시킨다.
2. fruit 브랜치를 main과 citrus 사이에 끼워 넣는다.
3. fruit에서 파생된 citrus 브랜치를 main 위로 옮겨붙인다.
4. citrus와 fruit를 합쳐 main 브랜치로 병합한다.
5. main 브랜치에서 fruit와 citrus를 동시에 cherry-pick한다.

정답: 3번

해설: `--onto` 옵션의 인자 순서는 `도착지(main)` → `출발지(fruit, 현재 citrus가 붙어있는 곳)` → `이동할 브랜치(citrus)`다. 즉, fruit에서 갈라진 citrus를 main 위로 재배치한다.

---

### Q3. `merge --squash`를 실행한 후 반드시 해야 하는 작업은?

1. `git push`로 원격에 반영한다.
2. `git stash`로 변경사항을 임시 저장한다.
3. `git commit`으로 수동으로 커밋을 생성한다.
4. `git branch -d`로 대상 브랜치를 삭제한다.
5. 아무것도 하지 않아도 자동으로 처리된다.

정답: 3번

해설: `--squash`는 변경사항을 staged 상태로만 만들어두고, 커밋은 자동으로 생성하지 않는다. 반드시 `git commit -m "메시지"`를 직접 실행해야 한다.

### Q4. 다음 중 GitHub Flow의 특징으로 가장 거리가 먼 것은?

1. main 브랜치 하나를 중심으로 운영된다.
2. Pull Request를 통한 코드 리뷰를 중시한다.
3. 상시 배포(CD) 환경에 적합하다.
4. develop, release, hotfix 등 여러 영구 브랜치를 유지한다.
5. 구조가 단순해 소규모 팀에 적합하다.

정답: 4번

해설: develop, release, hotfix 브랜치를 유지하는 것은 Git Flow의 특징이다. GitHub Flow는 main + 단기 topic 브랜치만 사용하는 단순한 구조를 지향한다.

### Q5. 일반 merge와 merge --squash의 결정적인 차이점은?

1. squash는 코드 변경사항이 반영되지 않는다.
2. squash는 충돌이 발생하지 않는다.
3. 코드 결과는 같지만, 커밋 히스토리 구조가 다르다.
4. 일반 merge는 staged 상태를 만들지 않는다.
5. squash는 원격 저장소에만 적용된다.

정답: 3번

해설: 두 방법 모두 최종 코드 상태는 동일하다. 차이는 히스토리다. 일반 merge는 두 브랜치가 이어붙여져 분기 이력이 남고, --squash는 대상 브랜치의 모든 커밋을 하나로 뭉쳐 새 커밋으로 추가하므로 브랜치 연결 관계가 남지 않는다.
