# 📚 Git 고급 활용법 - 커밋 관리 완벽 정리

> **학습 목표**: 실무에서 자주 사용하는 Git의 세밀한 커밋 관리 기법을 익힌다

---

## 1️⃣ 커밋 메시지 작성 스타일

### 📝 Conventional Commit (실무 표준)

**언제 쓰나요?**
- 팀 프로젝트에서 커밋 히스토리를 일관성 있게 관리할 때
- 자동화 도구(changelog 생성 등)를 사용할 때
- 코드 리뷰 시 변경사항을 빠르게 파악하고 싶을 때

**형식**: `타입: 설명`

| 타입 | 사용 시점 | 예시 |
|------|-----------|------|
| `feat` | 새 기능 구현 | `feat: 로그인 기능 추가` |
| `fix` | 버그 해결 | `fix: 로그인 시 토큰 만료 오류 수정` |
| `docs` | 문서 작업 | `docs: README에 설치 방법 추가` |
| `style` | 코드 스타일 정리 | `style: 들여쓰기 통일` |
| `refactor` | 기능 변경 없이 코드 개선 | `refactor: 중복 함수 제거` |
| `perf` | 성능 향상 | `perf: 이미지 로딩 속도 개선` |
| `test` | 테스트 코드 | `test: 로그인 유닛 테스트 추가` |
| `chore` | 빌드/설정 변경 | `chore: webpack 설정 업데이트` |

### 🎨 Emoji Commit (가독성 중심)

**언제 쓰나요?**
- 개인 프로젝트나 소규모 팀에서 커밋을 시각적으로 구분하고 싶을 때
- GitHub 등에서 커밋 로그를 더 예쁘게 보고 싶을 때

| 이모지 | 의미 | 사용 예시 |
|--------|------|-----------|
| ✨ | 새 기능 | `✨ 다크모드 추가` |
| 🐛 | 버그 수정 | `🐛 모바일 레이아웃 깨짐 수정` |
| 📚 | 문서 | `📚 API 문서 작성` |
| 🎨 | 코드 개선 | `🎨 컴포넌트 구조 개선` |
| ✅ | 테스트 | `✅ E2E 테스트 추가` |
| 📦 | 의존성/빌드 | `📦 React 18로 업그레이드` |

## 2️⃣ 세밀한 스테이징: Hunk 단위로 나누기

### 🎯 `git add -p` - 부분 스테이징

**언제 필요한가요?**
- 한 파일에 여러 종류의 변경사항이 섞여 있을 때
- 논리적으로 다른 작업을 별도 커밋으로 분리하고 싶을 때
- 실수로 디버깅 코드를 커밋하지 않으려 할 때

**사용법**:
```bash
git add -p
```

**대화형 옵션**:
- `y` - 이 hunk를 스테이징
- `n` - 이 hunk를 건너뛰기
- `s` - hunk를 더 작은 단위로 분할
- `q` - 종료
- `?` - 도움말 보기

**실전 시나리오**:
```bash
# 상황: tigers.yaml에서 manager와 members를 동시에 수정했지만
# manager 변경만 먼저 커밋하고 싶다면?

git add -p tigers.yaml
# → manager 부분만 'y' 선택
# → members 부분은 'n' 선택

git commit -m "feat: Tigers 매니저 변경"
# 나중에 members 변경을 별도 커밋
```

### 📋 `git commit -v` - 변경사항 확인하며 커밋

**언제 쓰나요?**
- 커밋 메시지를 작성하면서 정확히 무엇을 변경했는지 다시 확인하고 싶을 때
- 실수로 원치 않는 변경사항을 포함하지 않았는지 검증할 때

```bash
git commit -v
```

**차이점**:
- `git diff --staged`: 커밋 전 확인만
- `git commit -v`: 에디터에서 diff를 **보면서** 메시지 작성

## 3️⃣ Stash: 작업 임시 보관하기

### 💾 기본 사용법

**언제 필요한가요?**
- 급하게 다른 브랜치로 전환해야 하는데 현재 작업은 커밋하기 애매할 때
- 실험적인 코드를 잠시 치워두고 싶을 때
- 브랜치를 잘못 선택해서 작업했을 때

```bash
# 현재 작업 치워두기
git stash

# 가장 최근 stash 다시 적용
git stash pop

# 적용하지만 stash는 유지
git stash apply
```

### 🔍 고급 활용

#### 선택적 Stash
```bash
# 일부만 stash (대화형)
git stash -p
```

**시나리오**: A, B, C 파일을 수정했는데 A만 stash하고 싶다면?

#### 메시지와 함께 저장
```bash
git stash -m "로그인 UI 실험 코드"
```

#### Stash 목록 관리
```bash
# 목록 보기
git stash list
# 출력 예: stash@{0}: WIP on main: 메시지
#         stash@{1}: On feature: 다른 작업

# 특정 stash 적용
git stash apply stash@{1}

# 특정 stash 삭제
git stash drop stash@{0}

# 모두 삭제
git stash clear
```

### ⚠️ 자주 하는 실수

**문제**: stash pop 후 충돌 발생
**해결**:
```bash
# 새 브랜치를 만들어서 적용
git stash branch my-stashed-work
```

## 4️⃣ 커밋 수정하기: `git commit --amend`

### ✏️ 마지막 커밋 고치기

**언제 쓰나요?**
- 커밋 직후 오타를 발견했을 때
- 빠뜨린 파일을 추가해야 할 때
- 커밋 메시지를 다시 작성하고 싶을 때

```bash
# 메시지만 수정 (에디터 열림)
git commit --amend

# 메시지를 명령어로 직접 수정
git commit --amend -m "수정된 메시지"

# 파일 추가하고 메시지는 그대로
git add forgotten-file.js
git commit --amend --no-edit
```

### 💡 실전 패턴

**상황 1**: 커밋 후 console.log 발견
```bash
# console.log 제거
git add .
git commit --amend --no-edit
```

**상황 2**: 커밋 메시지 오타
```bash
git commit --amend -m "fix: 오류 메시지 오타 수정"
```

### ⚠️ 주의사항

**이미 push한 커밋은 amend하지 마세요!**
- 다른 사람과 공유한 커밋을 수정하면 히스토리가 꼬입니다
- 로컬에서만 작업한 커밋만 수정하세요

## 5️⃣ 과거 커밋 편집: `git rebase -i`

### 🔧 대화형 리베이스

**언제 쓰나요?**
- 여러 개의 작은 커밋을 하나로 합치고 싶을 때 (squash)
- 과거 커밋 메시지를 수정하고 싶을 때
- 불필요한 커밋을 삭제하고 싶을 때
- 커밋을 더 작은 단위로 나누고 싶을 때

```bash
# 최근 3개 커밋 수정
git rebase -i HEAD~3

# 특정 커밋 이후 모두 수정
git rebase -i [커밋해시]
```

### 📖 명령어 가이드

| 명령어 | 용도 | 사용 시점 |
|--------|------|-----------|
| `p` (pick) | 커밋 유지 | 그대로 두고 싶을 때 |
| `r` (reword) | 메시지 변경 | 오타 수정, 설명 개선 |
| `e` (edit) | 커밋 수정 | 파일 추가/제거, 분할 |
| `s` (squash) | 이전 커밋에 합치기 | 여러 작은 커밋 통합 |
| `f` (fixup) | 합치기 (메시지 버림) | typo 수정 커밋 등 |
| `d` (drop) | 커밋 삭제 | 실수로 만든 커밋 제거 |

### 🎬 실전 예제

#### 예제 1: 커밋 메시지 수정
```bash
git rebase -i HEAD~3

# 에디터에서:
pick abc1234 횻홍
pick def5678 기능 추가
pick ghi9012 버그 수정

# 변경:
r abc1234 횻홍  # ← r로 변경
pick def5678 기능 추가
pick ghi9012 버그 수정

# 저장 후 다음 에디터에서 "버그 수정"으로 변경
```

#### 예제 2: 여러 커밋 합치기
```bash
git rebase -i HEAD~4

# 에디터:
pick aaa1111 캐릭터 추가
pick bbb2222 스킬 구현
pick ccc3333 밸런스 조정
pick ddd4444 테스트 완료

# 변경 (캐릭터 관련 커밋 통합):
pick aaa1111 캐릭터 추가
s bbb2222 스킬 구현
s ccc3333 밸런스 조정
pick ddd4444 테스트 완료

# 저장 후 통합된 커밋 메시지 작성
```

#### 예제 3: 커밋 분할하기
```bash
git rebase -i HEAD~2

# 에디터:
pick xxx1111 UI와 로직 동시 작업
pick yyy2222 테스트 추가

# 변경:
e xxx1111 UI와 로직 동시 작업  # ← e로 변경
pick yyy2222 테스트 추가

# 저장 후:
git reset HEAD~
# 이제 변경사항이 unstaged 상태

git add ui-file.js
git commit -m "feat: UI 컴포넌트 추가"

git add logic-file.js
git commit -m "feat: 비즈니스 로직 구현"

git rebase --continue
```

#### 예제 4: 불필요한 커밋 삭제
```bash
git rebase -i HEAD~3

# 에디터:
pick zzz1111 기능 구현
pick zzz2222 뻘짓
pick zzz3333 버그 수정

# 변경:
pick zzz1111 기능 구현
d zzz2222 뻘짓  # ← d로 변경하거나 줄 자체를 삭제
pick zzz3333 버그 수정
```

### ⚠️ 리베이스 주의사항

1. **이미 push한 커밋은 리베이스하지 마세요**
    - 팀원들과 히스토리가 꼬입니다
    - 로컬에서만 작업한 커밋만 수정

2. **충돌 발생 시**
   ```bash
   # 충돌 해결 후
   git add .
   git rebase --continue
   
   # 취소하고 싶다면
   git rebase --abort
   ```

3. **edit 모드에서 작업 중단하지 마세요**
    - 반드시 `git rebase --continue` 또는 `--abort`로 마무리

## 📌 핵심 요약

### 🎯 상황별 빠른 참조

| 상황 | 명령어 | 비고 |
|------|--------|------|
| 일부만 스테이징 | `git add -p` | 대화형으로 선택 |
| 변경사항 보며 커밋 | `git commit -v` | diff 확인하며 메시지 작성 |
| 작업 임시 보관 | `git stash` | 브랜치 전환 전 |
| 일부만 임시 보관 | `git stash -p` | 선택적 stash |
| 마지막 커밋 수정 | `git commit --amend` | push 전에만! |
| 파일 추가만 | `git commit --amend --no-edit` | 메시지 유지 |
| 과거 커밋 수정 | `git rebase -i HEAD~N` | N개 커밋 편집 |
| 커밋 합치기 | rebase 후 `s` 또는 `f` | squash/fixup |
| 커밋 분할 | rebase 후 `e` + reset | edit 모드 |

### 💡 헷갈리는 포인트

**Stash vs Commit**
- Stash: 임시 보관 (커밋 히스토리에 안 남음)
- Commit: 영구 기록

**Squash vs Fixup**
- Squash: 메시지를 새로 작성
- Fixup: 이전 커밋 메시지 사용 (자잘한 수정용)

**Amend vs Rebase**
- Amend: 마지막 커밋만 수정
- Rebase: 여러 과거 커밋 수정

**Apply vs Pop**
- Apply: stash 유지하며 적용
- Pop: 적용 후 stash 삭제

## 🧪 복습 퀴즈

### Q1. 한 파일에서 여러 종류의 변경사항이 있을 때, 일부만 선택적으로 스테이징하려면 어떤 명령어를 사용해야 하나요?

1. `git add -a`
2. `git add -p`
3. `git add --select`
4. `git stash -p`
5. `git commit -v`

**정답: 2번**

`git add -p`는 patch 모드로 hunk 단위로 선택적 스테이징이 가능합니다. 대화형으로 각 변경사항을 y/n으로 선택할 수 있어, 논리적으로 다른 작업을 별도 커밋으로 분리할 때 유용합니다. 4번의 `git stash -p`는 선택적 stash에 사용됩니다.

### Q2. 다음 중 이미 원격 저장소에 push한 커밋에 대해 절대 하지 말아야 할 작업은?

1. `git log`로 히스토리 확인
2. `git show`로 커밋 내용 보기
3. `git rebase -i`로 커밋 수정
4. `git diff`로 변경사항 비교
5. `git blame`으로 작성자 확인

**정답: 3번**

이미 push한 커밋을 `git rebase -i`나 `git commit --amend`로 수정하면 커밋 히스토리가 변경되어 협업 중인 팀원들의 작업과 충돌이 발생합니다. 이는 심각한 문제를 일으킬 수 있으므로 로컬에서만 작업한 커밋에만 사용해야 합니다. 1, 2, 4, 5번은 모두 읽기 전용 명령어로 안전합니다.

---

### Q3. 급하게 다른 브랜치로 전환해야 하는데 현재 작업 중인 코드는 커밋하기 애매한 상황입니다. 가장 적절한 방법은?

1. 강제로 브랜치 전환 (`git checkout -f`)
2. 미완성 코드라도 일단 커밋
3. `git stash`로 작업 임시 보관
4. 변경사항을 모두 삭제
5. 새 브랜치를 만들어 커밋

**정답: 3번**

`git stash`는 현재 작업을 임시로 안전하게 보관하는 명령어입니다. 나중에 `git stash pop`으로 다시 불러올 수 있어, 미완성 작업을 커밋하지 않고도 브랜치를 자유롭게 전환할 수 있습니다. 1번은 작업 내용을 잃게 되고, 2번은 불완전한 커밋이 히스토리에 남습니다.

### Q4. `git rebase -i`에서 여러 작은 커밋을 하나로 합치면서 새로운 커밋 메시지를 작성하고 싶을 때 사용하는 명령어는?

1. `p` (pick)
2. `r` (reword)
3. `f` (fixup)
4. `s` (squash)
5. `d` (drop)

**정답: 4번**

`s` (squash)는 해당 커밋을 이전 커밋과 합치면서 새로운 메시지를 작성할 수 있게 합니다. 반면 `f` (fixup)는 합치되 이전 커밋의 메시지를 그대로 사용합니다. "WIP" 같은 임시 커밋들을 하나로 정리할 때 squash를 사용하면 깔끔한 커밋 메시지를 작성할 수 있습니다.

### Q5. 마지막 커밋에 빠뜨린 파일을 추가하되, 커밋 메시지는 그대로 유지하고 싶습니다. 올바른 명령어 순서는?

1. `git add file.js` → `git commit --amend`
2. `git add file.js` → `git commit --amend --no-edit`
3. `git commit --amend` → `git add file.js`
4. `git stash` → `git commit --amend`
5. `git add file.js` → `git rebase -i HEAD~1`

**정답: 2번**

먼저 `git add`로 빠뜨린 파일을 스테이징한 후, `git commit --amend --no-edit`를 사용하면 에디터를 열지 않고 기존 메시지를 유지하면서 파일만 추가할 수 있습니다. `--no-edit` 플래그가 핵심입니다. 1번은 에디터가 열려 번거롭고, 3번은 순서가 잘못되었습니다.
