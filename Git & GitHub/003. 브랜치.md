# Git 브랜치 완벽 정리 📚

## 🌿 브랜치란?

브랜치는 **독립적인 작업 공간**입니다. 원본 코드를 건드리지 않고 새로운 기능을 개발하거나 실험할 수 있게 해줍니다.

> 💡 **실무에서는 언제 쓰나요?**
> - 새 기능 개발할 때 (feature/login, feature/payment)
> - 버그 수정할 때 (fix/header-bug)
> - 실험적인 코드 작성할 때
> - 여러 명이 동시에 작업할 때

---

## 1️⃣ 브랜치 기본 조작

### 📌 브랜치 생성

```bash
git branch <브랜치명>
```

**예시**
```bash
git branch add-coach
```

### 🔄 브랜치 이동

```bash
git switch <브랜치명>
```

**생성과 동시에 이동하기** (더 자주 씀!)
```bash
git switch -c <새브랜치명>
```

### 📋 브랜치 목록 확인

```bash
git branch
```
- `*` 표시가 현재 위치한 브랜치

### 🗑️ 브랜치 삭제

**일반 삭제** (merge 완료된 브랜치)
```bash
git branch -d <브랜치명>
```

**강제 삭제** (merge 안 된 브랜치)
```bash
git branch -D <브랜치명>
```

### ✏️ 브랜치 이름 변경

```bash
git branch -m <기존이름> <새이름>
```

## 2️⃣ 브랜치 합치기: Merge vs Rebase

### 🔀 Merge (병합)

**언제 사용?**
- 협업할 때 (여러 사람의 작업 내역을 남기고 싶을 때)
- 기능 개발이 끝났을 때
- 작업 히스토리를 보존하고 싶을 때

**사용법**
```bash
# main 브랜치로 이동
git switch main

# 다른 브랜치를 main으로 병합
git merge <브랜치명>
```

**특징**
- ✅ 병합 커밋이 생성됨
- ✅ 모든 작업 이력이 그대로 남음
- ✅ 직관적이고 안전함
- ❌ 커밋 히스토리가 복잡해질 수 있음

**되돌리기**
```bash
# merge도 커밋이므로 reset으로 되돌릴 수 있음
git reset --hard HEAD~1
```

---

### 🔁 Rebase (재배치)

**언제 사용?**
- 혼자 작업할 때
- 깔끔한 커밋 히스토리를 원할 때
- 작업 내용을 정리하고 싶을 때

**사용법**
```bash
# feature 브랜치로 이동 (⚠️ merge와 반대!)
git switch feature

# main의 최신 상태를 기준으로 재배치
git rebase main

# main으로 이동
git switch main

# fast-forward 병합
git merge feature
```

**특징**
- ✅ 깔끔한 일직선 히스토리
- ✅ 커밋 순서가 정리됨
- ❌ 공유된 브랜치에서 사용하면 위험 (⚠️ 절대 금지!)
- ❌ 충돌 해결이 복잡할 수 있음

---

### ⚖️ Merge vs Rebase 비교표

| 구분 | Merge | Rebase |
|------|-------|--------|
| **히스토리** | 복잡하지만 정확함 | 깔끔하지만 변경됨 |
| **협업** | ✅ 적합 | ❌ 위험 |
| **작업 위치** | main에서 실행 | feature에서 실행 |
| **되돌리기** | 쉬움 | 어려움 |

## 3️⃣ 충돌 해결하기 ⚠️

### 🤔 충돌은 언제 발생하나?

같은 파일의 같은 줄을 서로 다르게 수정했을 때 발생합니다.

**예시 상황**
```
main 브랜치: manager를 "Kenneth"로 변경
feature 브랜치: manager를 "Deborah"로 변경
→ Git은 어떤 걸 선택해야 할지 모름!
```

---

### 🔧 Merge 충돌 해결

**1단계: 충돌 발생**
```bash
git merge conflict-branch
# Auto-merging tigers.yaml
# CONFLICT (content): Merge conflict in tigers.yaml
```

**2단계: 상태 확인**
```bash
git status
# Unmerged paths:
#   both modified: tigers.yaml
```

**3단계: 파일 열어서 확인**
```yaml
<<<<<<< HEAD
manager: Kenneth
=======
manager: Deborah
>>>>>>> conflict-branch
```

**4단계: 원하는 내용으로 수정**
```yaml
manager: Kenneth  # 또는 Deborah, 또는 다른 값
```

**5단계: 충돌 해결 완료**
```bash
git add .
git commit
```

**중단하고 싶을 때**
```bash
git merge --abort
```

---

### 🔧 Rebase 충돌 해결

**1단계: 충돌 발생**
```bash
git rebase main
```

**2단계: 파일 수정 후**
```bash
git add .
git rebase --continue
```
- 충돌이 여러 개면 이 과정을 반복!

**중단하고 싶을 때**
```bash
git rebase --abort
```

## 4️⃣ 유용한 명령어 모음

### 📊 브랜치 시각화

```bash
# 모든 브랜치의 커밋 히스토리를 그래프로 보기
git log --all --decorate --oneline --graph
```

**축약 alias 만들기**
```bash
# .gitconfig에 추가
git config --global alias.graph "log --all --decorate --oneline --graph"

# 이후 사용
git graph
```

- [ ] main 브랜치로 이동했는가?

- [ ] feature 브랜치로 이동했는가? (⚠️ 중요!)

- [ ] main에서 fast-forward merge를 진행했는가?
- [ ] 충돌이 모두 해결되었는가?

## 🚨 자주 하는 실수

### 1. Rebase를 공유 브랜치에서 사용
```bash
# ❌ 절대 하지 마세요!
git switch main
git rebase feature  # 다른 사람들의 작업과 충돌!
```

### 2. Merge 방향 착각
```bash
# ❌ 잘못된 방향
git switch feature
git merge main  # feature에 main을 병합?

# ✅ 올바른 방향
git switch main
git merge feature  # main에 feature를 병합
```

### 3. 충돌 마커 그대로 커밋
```yaml
# ❌ 이대로 커밋하면 안 됨!
<<<<<<< HEAD
manager: Kenneth
=======
manager: Deborah
>>>>>>> conflict-branch
```

## 💡 핵심 요약

### 브랜치 생성 & 이동
```bash
git switch -c <브랜치명>  # 생성과 동시에 이동 (가장 많이 씀!)
```

### 병합 방법 선택
- **Merge**: 협업, 안전, 이력 보존 → 실무 기본
- **Rebase**: 혼자 작업, 깔끔한 히스토리 → 선택적 사용

### 충돌 해결 공식
1. 충돌 발생 확인 (`git status`)
2. 파일 열어서 수정
3. `git add .`
4. `git commit` (merge) 또는 `git rebase --continue` (rebase)

### 기억할 것 3가지
1. **Rebase는 공유 브랜치에서 절대 금지** ⛔
2. **Merge는 main에서, Rebase는 feature에서** 🔄
3. **충돌 나면 당황하지 말고 차근차근** 🧘

## 📝 복습 퀴즈

### Q1. 브랜치를 생성하면서 동시에 이동하는 명령어는?

A) `git branch -c new-feature`  
B) `git switch -c new-feature`  
C) `git checkout new-feature`  
D) `git create new-feature`

**정답: B**  
`git switch -c <브랜치명>`은 브랜치 생성과 이동을 한 번에 처리합니다. `-c`는 create의 약자입니다. 참고로 `git checkout -b`도 같은 기능이지만, Git 2.23 버전부터는 `switch`를 권장합니다.

---

### Q2. 다음 중 Merge와 Rebase에 대한 설명으로 올바른 것은?

A) Merge는 feature 브랜치에서, Rebase는 main 브랜치에서 실행한다  
B) Merge는 커밋 히스토리를 변경하지만, Rebase는 보존한다  
C) Merge는 병합 커밋이 생성되고, Rebase는 일직선 히스토리가 된다  
D) Rebase는 공유 브랜치에서 사용하기 안전하다

**정답: C**  
Merge는 병합 커밋을 생성하여 모든 이력을 보존하고, Rebase는 커밋을 재배치하여 깔끔한 일직선 히스토리를 만듭니다. A는 반대입니다 (Merge는 main에서, Rebase는 feature에서 실행). B도 반대입니다. D는 틀렸습니다 - Rebase는 공유 브랜치에서 절대 사용하면 안 됩니다.

---

### Q3. Git에서 충돌이 발생하는 경우는?

A) 서로 다른 파일을 수정했을 때  
B) 같은 파일의 다른 줄을 수정했을 때  
C) 같은 파일의 같은 줄을 다르게 수정했을 때  
D) 새로운 파일을 추가했을 때

**정답: C**  
충돌은 같은 파일의 같은 위치(줄)를 서로 다르게 수정했을 때 발생합니다. Git이 어떤 변경사항을 선택해야 할지 판단할 수 없기 때문입니다. A와 B는 자동으로 병합되며, D는 충돌이 발생하지 않습니다.

---

### Q4. Merge 진행 중 충돌이 발생했을 때, 병합을 취소하고 이전 상태로 돌아가는 명령어는?

A) `git merge --cancel`  
B) `git merge --abort`  
C) `git reset --hard`  
D) `git revert merge`

**정답: B**  
`git merge --abort`는 진행 중인 병합을 취소하고 병합 시작 전 상태로 돌아갑니다. Rebase의 경우에도 `git rebase --abort`로 동일하게 취소할 수 있습니다.

### Q5. 다음 중 브랜치 삭제 명령어에 대한 설명으로 올바른 것은?

A) `git branch -d`는 merge 여부와 관계없이 항상 삭제된다  
B) `git branch -D`는 merge되지 않은 브랜치도 강제로 삭제한다  
C) 브랜치 삭제는 취소할 수 없다  
D) 현재 위치한 브랜치도 삭제할 수 있다

**정답: B**  
`-d`(소문자)는 안전 삭제로 merge된 브랜치만 삭제하고, `-D`(대문자)는 강제 삭제로 merge 여부와 관계없이 삭제합니다. C는 틀렸습니다 - reflog를 통해 복구 가능합니다. D도 틀렸습니다 - 현재 위치한 브랜치는 삭제할 수 없습니다.

### Q6. 실무에서 새로운 기능을 개발할 때 권장되는 작업 순서는?

A) main 브랜치에서 직접 작업 → commit → push  
B) feature 브랜치 생성 → 작업 → commit → main으로 merge  
C) feature 브랜치 생성 → 작업 → main으로 rebase → push  
D) main 브랜치를 feature로 merge → 작업 → commit

**정답: B**  
실무에서는 main 브랜치를 보호하기 위해 feature 브랜치에서 작업한 후 merge하는 것이 일반적입니다. Rebase는 혼자 작업할 때 선택적으로 사용하며, 공유 브랜치에서는 merge가 더 안전합니다.
