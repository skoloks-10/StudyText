## 1️⃣ README.md — 프로젝트 문서화

### 📌 왜 쓰는가?
GitHub에 레포지토리를 올렸을 때, 방문자가 가장 먼저 보는 파일이 `README.md`다.
프로젝트 소개, 설치 방법, 사용법 등을 정리해 두면 협업과 공유가 훨씬 쉬워진다.

### ✍️ 작성 방법 순서
1. 프로젝트 최상위 폴더에 `README.md` 파일 생성
2. VS Code에서 **미리보기** 확인 (단축키: `Ctrl+Shift+V` / `Cmd+Shift+V`)
3. Git에 push → GitHub 레포 페이지에서 자동 렌더링 확인
4. 필요하면 하위 폴더마다 별도 `README.md` 추가 가능

### ⭐ 마크다운 핵심 문법 (Notion에서도 동일하게 작동)

| 문법 | 결과 |
|------|------|
| `# 제목` | H1 헤딩 |
| `## 소제목` | H2 헤딩 |
| `**굵게**` | 굵은 글씨 |
| `*기울임*` | 이탤릭체 |
| `` `코드` `` | 인라인 코드 |
| `- 항목` | 순서 없는 목록 |
| `1. 항목` | 순서 있는 목록 |
| `[링크텍스트](URL)` | 하이퍼링크 |
| `![대체텍스트](이미지경로)` | 이미지 삽입 |

📎 참고: [markdownguide.org](https://www.markdownguide.org/cheat-sheet/) / [GitHub 공식 가이드](https://docs.github.com/en/github/writing-on-github/getting-started-with-writing-and-formatting-on-github/basic-writing-and-formatting-syntax)

## 2️⃣ Pull Request (PR)

### 📌 언제 쓰는가?
코드 변경사항을 `main` 브랜치에 바로 merge하지 않고, **팀원의 리뷰를 거친 후 합치고 싶을 때** 사용한다.

> 💡 실무에서는 혼자 작업해도 PR을 통해 변경 이력을 남기는 경우가 많다.

### 🔄 PR 생성 흐름

```
새 브랜치 생성 → 변경사항 커밋 → push → GitHub에서 PR 생성
```

1. 새 브랜치에서 작업 후 `git push`
2. GitHub 레포 페이지 → `Compare & pull request` 버튼 클릭
   - 또는 `~ branches` 탭 → `New pull request`
3. 제목 & 설명 작성 → `Create pull request` 클릭

### ✅ PR 검토 및 처리 흐름

1. 레포 상단 `Pull requests` 탭 클릭
2. PR 내용 확인
   - 의견 있을 때 → 코멘트 달기
   - 반려해야 할 때 → `Close pull request`
   - 승인할 때 → `Merge pull request`

### ⚠️ 자주 헷갈리는 포인트
- PR은 **브랜치 → 브랜치** 요청이다. 직접 파일을 주고받는 게 아님
- PR을 merge해도 원본 브랜치는 삭제되지 않는다 (직접 삭제해야 함)
- `Merge pull request` 전에 충돌(conflict)이 있으면 먼저 해결해야 함

## 3️⃣ 오픈소스에 기여하기

### 📌 왜 하는가?
실제 사람들이 쓰는 코드에 기여하면서 실력을 키우고, 커뮤니티에 참여할 수 있다.
이력서에 기재할 수 있는 실질적인 포트폴리오가 된다.

### 🔑 기여 전 필수 확인
각 프로젝트마다 기여 방식이 다르므로 반드시 **CONTRIBUTING.md** 또는 README의 기여 가이드를 먼저 읽는다.
예: [React 레포 기여 가이드](https://github.com/facebook/react)

### 🍴 Fork → 수정 → PR 흐름

```
원본 레포 Fork → 내 계정에 복사됨 → 수정 → 원본 레포로 PR 요청
```

1. 원하는 레포에서 `Fork` 버튼 클릭 → 내 계정으로 복사됨
2. 내 포크 레포를 로컬에 `clone`
3. 코드 수정 후 `push`
4. 원본 레포에 **Pull Request** 보내기

### 👑 오픈소스 관리자 관점
PR을 받으면 관리자는 코드 검토 후:
- 코멘트로 수정 요청
- `Close pull request` (반려)
- `Merge pull request` (수락)

## 4️⃣ GitHub Pages — 내 웹사이트 무료 호스팅

### 📌 언제 쓰는가?
포트폴리오 사이트, 프로젝트 소개 페이지, 간단한 정적 웹사이트를 **무료로 인터넷에 올리고 싶을 때** 사용한다.

### 🚀 내 GitHub Page 만드는 순서

1. **레포지토리 이름 규칙 필수** ❗
   - 반드시 `(내 GitHub 아이디).github.io` 로 생성
   - 예: 아이디가 `jinyoung`이면 → `jinyoung.github.io`

2. 레포를 로컬에 `clone`

3. 최상위 폴더에 `index.html` 작성
   - VS Code 팁: 빈 html 파일에서 `!` 입력 후 `Enter` → 기본 템플릿 자동 생성

4. 작성 후 `git push`

5. `https://(내 아이디).github.io` 접속
   - ⏳ 최초 배포 시 수분~수십 분 소요될 수 있음

### ⚠️ 자주 헷갈리는 포인트
- 레포 이름이 정확히 `아이디.github.io` 가 아니면 페이지가 활성화되지 않는다
- 수정 후 push해도 반영까지 약간의 시간이 걸린다
- 기본적으로 **정적 파일만** 호스팅 가능 (서버 로직 X)

## 🧠 복습 퀴즈

### Q1. README.md에 대한 설명으로 옳지 않은 것은?

1. GitHub 레포지토리 페이지에서 자동으로 렌더링된다
2. 마크다운(.md) 문법으로 작성한다
3. 반드시 프로젝트 최상위 폴더에만 하나만 존재해야 한다
4. VS Code에서 미리보기 기능으로 확인할 수 있다
5. 하위 폴더에도 별도의 README.md를 만들 수 있다

정답: 3번

해설: README.md는 최상위 폴더 외에도 하위 폴더마다 별도로 만들 수 있다. "하나만 존재해야 한다"는 설명은 틀렸다. 나머지 설명은 모두 올바르다.

---

### Q2. Pull Request(PR)를 올바르게 설명한 것은?

1. 코드를 main 브랜치에 즉시 적용하는 기능이다
2. 변경사항을 merge하기 전에 팀원의 리뷰를 거치기 위한 기능이다
3. PR을 생성하면 자동으로 merge가 완료된다
4. PR은 같은 브랜치 내에서만 사용 가능하다
5. PR은 반드시 두 명 이상이 있어야 사용할 수 있다

정답: 2번

해설: PR의 핵심 목적은 코드를 바로 merge하지 않고 리뷰를 거치는 것이다. 생성만으로 자동 merge되지 않으며, 다른 브랜치 간에 사용하는 기능이다. 혼자 작업하는 환경에서도 이력 관리 목적으로 사용 가능하다.

---

### Q3. 오픈소스 프로젝트에 코드를 기여하는 올바른 순서는?

1. PR 요청 → Fork → 코드 수정 → push
2. 코드 수정 → Fork → push → PR 요청
3. Fork → 코드 수정 → push → PR 요청
4. Fork → PR 요청 → 코드 수정 → push
5. 코드 수정 → PR 요청 → Fork → push

정답: 3번

해설: 오픈소스 기여의 순서는 Fork(내 계정으로 복사) → 코드 수정 → push(내 포크 레포에) → 원본 레포로 PR 요청이다. Fork 없이 바로 원본 레포를 수정할 수 없다.

### Q4. GitHub Pages를 사용하기 위해 레포지토리 이름을 올바르게 지은 것은? (GitHub 아이디: `devjiny` 기준)

1. `github-pages-devjiny`
2. `devjiny-github-io`
3. `devjiny.github.io`
4. `pages.devjiny.github`
5. `devjiny_github_io`

정답: 3번

해설: GitHub Pages의 개인 페이지를 활성화하려면 레포지토리 이름이 정확히 `(아이디).github.io` 형식이어야 한다. 하이픈이나 언더바로 대체하면 페이지가 활성화되지 않는다.

---

### Q5. GitHub Pages에 대한 설명으로 옳지 않은 것은?

1. 계정당 무료로 웹 호스팅이 가능하다
2. index.html 파일을 최상위 디렉토리에 놓으면 기본 페이지로 작동한다
3. push 후 사이트에 즉시 반영되므로 기다릴 필요가 없다
4. 정적 파일(HTML, CSS, JS)을 호스팅하는 데 적합하다
5. VS Code에서 `!` + Enter로 기본 HTML 템플릿을 빠르게 생성할 수 있다

정답: 3번

해설: GitHub Pages는 push 후 실제 사이트에 반영되기까지 수 분에서 수십 분이 걸릴 수 있다. 즉시 반영된다는 설명은 틀렸다. 특히 최초 배포 시 시간이 더 걸린다.
