## 1️⃣ HTTP 헤더란?

HTTP 메시지의 두 번째 줄, **필드 라인**에 명시되는 정보들이다.

```
형식: 헤더이름: 헤더값
예시: Host: info.cern.ch
```

헤더는 크게 세 가지 상황에서 사용된다.
- 요청(Request) 시 주로 쓰는 헤더
- 응답(Response) 시 주로 쓰는 헤더
- 요청 + 응답 모두에서 쓰는 헤더

---

## 2️⃣ 요청 시 활용되는 헤더

### 🏠 Host
- 요청을 보낼 서버의 **도메인 + 포트 번호** 명시
- 예: `Host: info.cern.ch`

### 🧑‍💻 User-Agent
- HTTP 요청을 보내는 **클라이언트 측 프로그램(브라우저 등) 정보** 포함
- 서버는 이를 통해 클라이언트의 접속 환경(OS, 브라우저 종류/버전) 파악 가능
- 예: `User-Agent: Mozilla/5.0 (Windows NT 10.0; Win64; x64) ...`

### 🔗 Referer
- 클라이언트가 **이전에 머물던 URL** 명시 → 유입 경로 파악에 유용
- 예: `Referer: https://en.wikipedia.org/`
- ⚠️ 주의: 영어 문법상 "Referrer"가 맞지만, 초기 오타로 **Referer**로 굳어짐

### 🔐 Authorization
- 클라이언트의 **인증 정보(자격 증명)** 담는 헤더
- 형식: `Authorization: <인증타입> <인증정보>`
- 가장 기본적인 인증 타입은 **Basic**
    - `username:password`를 **Base64 인코딩**한 값 전송
    - 예: `Authorization: Basic bWluY2hul...`
- ⚠️ 주의: Base64는 암호화가 아니라 단순 변환이므로 보안에 취약할 수 있음

## 3️⃣ 응답 시 활용되는 헤더

### 🖥️ Server
- 요청을 처리하는 **서버 소프트웨어 정보**
- 예: `Server: Apache/2.4.1 (Unix)`

### ✅ Allow
- 클라이언트에게 **허용된 HTTP 메서드** 알려줌
- 상태 코드 **405 (Method Not Allowed)** 응답 시 함께 전송됨
- 예: `Allow: POST, OPTIONS`

### ⏰ Retry-After
- 상태 코드 **503 (Service Unavailable)** 응답 시 사용
- **자원을 이용 가능한 날짜 또는 초(秒)** 명시
- 예: `Retry-After: Fri, 23 Aug 2024 09:00:00 GMT` 또는 `Retry-After: 120`

### 📍 Location
- 클라이언트에게 **자원의 위치** 알려줌
- 주로 **리다이렉션** 발생 시 or 새 자원이 생성되었을 때 사용

### 🔒 WWW-Authenticate
- 상태 코드 **401 (Unauthorized)** 와 함께 전송
- 자원에 접근하기 위한 **인증 방식** 설명
- 예: `WWW-Authenticate: Basic realm="Access to engineering site", charset="UTF-8"`
- realm: 보안이 적용되는 영역(접근 가능한 사용자 범위)

#### HTTP Basic 인증 흐름

```
클라이언트 → GET 요청 → 서버
서버 → 401 + WWW-Authenticate 헤더 → 클라이언트
클라이언트 → 사용자 ID/비밀번호 입력 받음
클라이언트 → GET + Authorization 헤더 → 서버
서버 → 인증 확인 후 200 OK 또는 401 응답
```

## 4️⃣ 요청 + 응답 모두에서 활용되는 헤더

### 📅 Date
- 메시지가 **생성된 날짜와 시각** 정보
- 예: `Date: Tue, 15 Nov 1994 08:12:31 GMT`

### 🔌 Connection
- 클라이언트-서버 간 **연결 방식** 설정
- `keep-alive`: 지속 연결 희망 (기본값)
- `close`: 연결 종료 희망

### 📏 Content-Length
- 메시지 본문의 **바이트 단위 크기**
- 예: `Content-Length: 100`

### 📄 Content-Type / Content-Language / Content-Encoding
이 세 헤더는 **표현 헤더(Representation Header)** 라고도 불린다.

| 헤더 | 역할 |
|------|------|
| Content-Type | 본문의 미디어 타입 + 문자 인코딩 명시 (예: `text/html; charset=UTF-8`) |
| Content-Language | 본문에 사용된 자연어 명시 (예: `ko`, `en-US`) |
| Content-Encoding | 본문의 압축/변환 방식 명시 (예: `gzip`, `deflate`, `br`) |

## 5️⃣ 캐시 (Cache)

### 캐시란?
> 불필요한 대역폭 낭비와 응답 지연을 방지하기 위해 **정보의 사본을 임시로 저장**하는 기술

- 동일한 요청에 캐시된 데이터를 활용 → 서버 재요청 없이 빠르게 응답
- **개인 전용 캐시**: 웹 브라우저에 저장
- **공용 캐시**: 클라이언트와 서버 사이의 중간 서버에 저장

### 캐시 신선도 (Freshness)
캐시는 원본이 아닌 "사본"이므로, 원본이 변경되면 사본이 낡아질 수 있다.  
캐시 데이터에 **유효 기간**을 설정하여 신선도 관리!

| 헤더 | 설명 |
|------|------|
| `Expires: <날짜>` | 만료 날짜 직접 지정 |
| `Cache-Control: max-age=<초>` | 유효 시간(초 단위)으로 지정 |

### 캐시 재검사 방법 1 — 날짜 기반 (If-Modified-Since)
캐시 만료 후 클라이언트가 서버에 **"이 날짜 이후로 변경됐어?"** 라고 물어봄

```
GET /index.html HTTP/1.1
Host: www.example.com
If-Modified-Since: Fri, 23 Aug 2024 09:00:00 GMT
```

서버 응답 결과:
| 상황 | 서버 응답 |
|------|---------|
| 자원이 변경됨 | 200 OK + 새 자원 |
| 자원이 변경 안 됨 | 304 Not Modified (본문 없음) |
| 자원이 삭제됨 | 404 Not Found |

### 캐시 재검사 방법 2 — ETag 기반 (If-None-Match)
ETag는 **자원의 버전을 식별하는 값** (자원 변경 시 ETag도 변경됨)

```
GET /index.html HTTP/1.1
Host: www.example.com
If-None-Match: "abc"
```

서버 응답 결과:
| 상황 | 서버 응답 |
|------|---------|
| Etag가 달라짐(변경됨) | 200 OK + 새 자원 + 새 Etag |
| Etag 동일(변경 안 됨) | 304 Not Modified |
| 자원 삭제됨 | 404 Not Found |

## 6️⃣ 쿠키 (Cookie)

### 쿠키란?
> HTTP는 **스테이트리스(stateless)** 프로토콜 → 상태 유지를 못 함  
> 이를 보완하기 위해 **서버가 생성해 클라이언트에 저장**시키는 데이터

- 기본 형태: `이름=값` + 속성들
- 서버 → Set-Cookie 헤더로 전달
- 클라이언트 → Cookie 헤더로 서버에 전송

### 쿠키 전달 흐름

```
[응답] Set-Cookie: name=minchul
[응답] Set-Cookie: phone=100-100

[요청] Cookie: name=minchul; phone=100-100
```

### 쿠키 주요 속성

| 속성 | 설명 |
|------|------|
| `domain=` | 쿠키를 사용할 수 있는 도메인 제한 |
| `path=` | 쿠키가 적용될 경로 제한 |
| `Expires=<날짜>` | 쿠키 만료 날짜 |
| `Max-Age=<초>` | 쿠키 유효 시간 (초 단위) |
| `Secure` | HTTPS 환경에서만 쿠키 전송 |
| `HttpOnly` | 자바스크립트에서 쿠키 접근 불가 (XSS 방어) |

### 쿠키의 보안 한계
- 쿠키는 HTTP 헤더에 노출 → 중간에서 탈취·조작 위험
- 해결: `Secure` + `HttpOnly` 속성으로 보완

### 세션 인증 (Session Authentication)
쿠키를 통해 세션 ID를 전달하여 **매 요청마다 로그인 없이** 인증 유지

```
① 클라이언트 → 인증 정보 전송
② 서버 → 세션 ID 생성 후 Set-Cookie로 전달
③ 서버 → 세션 ID를 DB 등에 저장
④ 클라이언트 → 이후 요청마다 Cookie에 세션 ID 포함
⑤ 서버 → 쿠키 속 세션 ID와 저장된 세션 ID 비교하여 인증
```

### 웹 스토리지 (쿠키와의 차이)
| 구분 | 쿠키 | 웹 스토리지 |
|------|------|------------|
| 서버 자동 전송 | O | X |
| 용량 | 작음 | 큼 |
| 만료 기간 | 있음 | 로컬: 없음 / 세션: 탭 닫으면 삭제 |

## 7️⃣ 콘텐츠 협상 (Content Negotiation)

### 콘텐츠 협상이란?
> 같은 URI에 대해 **클라이언트가 선호하는 형태의 표현**을 제공하는 메커니즘

예: 한국어 계정으로 접속 → 한국어 페이지, 영어 계정으로 접속 → 영어 페이지

### 관련 헤더

| 헤더 | 역할 |
|------|------|
| `Accept` | 선호하는 미디어 타입 (예: `text/html`) |
| `Accept-Language` | 선호하는 언어 (예: `ko`) |
| `Accept-Charset` | 선호하는 문자 인코딩 |
| `Accept-Encoding` | 선호하는 압축 방식 |

### q값 (Quality Value)
선호도에 **우선순위** 부여 가능 → 생략 시 기본값 1, 범위 0~1, 클수록 높은 우선순위

```
Accept-Language: ko-KR,ko;q=0.9,en-US;q=0.8,en;q=0.7
Accept: text/html,application/xml;q=0.9,text/plain;q=0.6,*/*;q=0.5
```

## 📌 핵심 요약 (빠른 복습용)

| 구분 | 헤더 | 핵심 역할 |
|------|------|---------|
| 요청 | Host | 도메인+포트 |
| 요청 | User-Agent | 브라우저/클라이언트 정보 |
| 요청 | Referer | 직전 페이지 URL |
| 요청 | Authorization | 인증 정보 (Basic = Base64) |
| 응답 | Server | 서버 소프트웨어 정보 |
| 응답 | Allow | 허용된 메서드 (405와 함께) |
| 응답 | Retry-After | 재시도 가능 시점 (503과 함께) |
| 응답 | Location | 리다이렉션 주소 |
| 응답 | WWW-Authenticate | 인증 방식 안내 (401과 함께) |
| 공통 | Date | 메시지 생성 시각 |
| 공통 | Connection | 연결 방식 (keep-alive/close) |
| 공통 | Content-Type | 본문 타입+인코딩 |
| 캐시 | Cache-Control | max-age로 유효 기간 설정 |

| 캐시 | ETag / If-None-Match | 버전 기반 캐시 재검사 |
| 쿠키 | Set-Cookie | 서버→클라이언트 쿠키 전달 |
| 쿠키 | Cookie | 클라이언트→서버 쿠키 전달 |
| 협상 | Accept-Language | 선호 언어 (q값으로 우선순위) |

## 🧪 복습용 퀴즈

### Q1. 다음 중 HTTP 요청 메시지에서 클라이언트의 이전 페이지 URL을 담는 헤더는?

1. Host
2. Authorization
3. Referer
4. User-Agent
5. Accept

정답: 3번 — Referer
해설: Referer 헤더는 클라이언트가 요청을 보낼 때 직전에 머물던 URL을 명시한다. 서버는 이를 통해 유입 경로를 파악할 수 있다. 영문법상으로는 Referrer가 맞지만 초기 오타로 Referer가 표준이 되었다.

---

### Q2. 상태 코드 401(Unauthorized)과 함께 사용되며, 클라이언트에게 인증 방식을 안내하는 헤더는?

1. Authorization
2. Allow
3. WWW-Authenticate
4. Server
5. Retry-After

정답: 3번 — WWW-Authenticate
해설: 서버가 401을 응답할 때 WWW-Authenticate 헤더로 "어떤 방식으로 인증하면 되는지"를 클라이언트에게 알려준다. 클라이언트는 이 정보를 보고 Authorization 헤더에 인증 정보를 담아 재요청한다.

---

### Q3. 캐시 신선도를 검사하는 방법 중 "ETag 기반"으로 서버에 물어볼 때 사용하는 요청 헤더는?

1. If-Modified-Since
2. If-None-Match
3. ETag
4. Cache-Control
5. Expires

정답: 2번 — If-None-Match
해설: If-None-Match 헤더에 현재 캐시된 자원의 ETag 값을 담아 서버에 전송한다. 서버는 이 ETag를 비교해 자원이 변경되지 않았다면 304 Not Modified를, 변경되었다면 200 OK와 새 자원을 응답한다.

---

### Q4. 쿠키의 HttpOnly 속성에 대한 설명으로 올바른 것은?

1. HTTPS 환경에서만 쿠키를 전송한다
2. 쿠키를 만료시키는 시간을 설정한다
3. 자바스크립트에서 쿠키에 접근하지 못하도록 제한한다
4. 쿠키를 특정 도메인에서만 사용 가능하게 한다
5. 쿠키를 특정 경로에서만 사용 가능하게 한다

정답: 3번 — 자바스크립트에서 쿠키에 접근하지 못하도록 제한한다
해설: 쿠키는 기본적으로 자바스크립트(document.cookie)로도 접근 가능하다. 악의적인 스크립트가 쿠키를 탈취할 수 있으므로, HttpOnly 속성으로 자바스크립트 접근을 차단해 보안을 강화한다. HTTPS 전용은 Secure 속성이다.

### Q5. 콘텐츠 협상에서 q값이 생략된 경우 그 의미는?

1. 해당 표현을 전혀 원하지 않음 (q=0)
2. 우선순위 없음
3. 가장 낮은 우선순위 (q=0.1)
4. 가장 높은 우선순위 (q=1)
5. 서버가 알아서 결정

정답: 4번 — 가장 높은 우선순위 (q=1)
해설: q(Quality Value)는 0부터 1 사이의 값으로, 클수록 선호도가 높다. q값이 생략되면 기본값 1로 처리되어 가장 높은 우선순위를 가진다.
