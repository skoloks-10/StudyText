# 📡 TCP와 UDP - 전송 계층 프로토콜

---

## 🎯 TCP vs UDP 한눈에 보기

**TCP (Transmission Control Protocol)**
- 신뢰할 수 있는 통신
- 연결 지향적
- 순서 보장, 재전송 기능
- 느리지만 정확함

**UDP (User Datagram Protocol)**
- 신뢰성 낮지만 빠름
- 비연결형
- 순서 보장 없음, 재전송 없음
- 실시간 통신에 적합

## 🔌 TCP 세그먼트 구조와 핵심 개념

### 📦 TCP 세그먼트 구성 요소

```
┌─────────────┬─────────────┬─────────────┐
│  송신 포트   │  수신 포트   │  순서 번호   │
├─────────────┼─────────────┼─────────────┤
│ 확인 응답 번호 │  제어 비트   │   윈도우    │
├─────────────┼─────────────┼─────────────┤
│   체크섬     │  긴급 포인터  │   옵션      │
└─────────────┴─────────────┴─────────────┘
```

### 🔢 순서 번호 (Sequence Number)

**언제 쓰나?**
- 데이터 송수신 시 각 세그먼트를 구분하기 위해
- 초기 순서 번호는 랜덤으로 생성 (보안상 이유)

**동작 방식:**
- 호스트 A가 초기 순서 번호 100으로 시작
- 500바이트 전송 → 다음 순서 번호는 600
- 호스트 B가 초기 순서 번호 8000으로 시작
- 1100바이트 전송 → 다음 순서 번호는 9100

### ✅ 확인 응답 번호 (Acknowledgment Number)

**언제 쓰나?**
- 상대방이 보낸 데이터를 잘 받았다고 알려줄 때
- "다음에 이 번호부터 보내줘"라는 의미

**헷갈리는 포인트:**
- 확인 응답 번호 = 받은 순서 번호 + 데이터 크기
- 예: 순서 번호 8000 + 데이터 1100바이트 → 확인 응답 9100

### 🚩 제어 비트 (Control Bits)

TCP 통신 제어를 위한 플래그들:

**ACK (Acknowledgment)**
- 세그먼트를 잘 받았다는 응답
- 거의 모든 세그먼트에 포함됨

**SYN (Synchronize)**
- 연결을 시작할 때 사용
- 초기 순서 번호 동기화

**FIN (Finish)**
- 연결을 종료할 때 사용

**기타:** RST, PSH, URG 등

### 📏 MSS와 MTU

**MSS (Maximum Segment Size)**
- TCP에서 한 번에 보낼 수 있는 최대 데이터 크기
- 일반적으로 1460바이트

**MTU (Maximum Transmission Unit)**
- 네트워크에서 전송 가능한 최대 크기
- 이더넷: 1500바이트

## 🤝 TCP 연결 수립 - 3-Way Handshake

### 흐름도

```
호스트 A                          호스트 B
   │                                 │
   │  ① SYN (연결 시작해요!)          │
   │ ──────────────────────────────> │
   │                                 │ LISTEN
   │  ② SYN + ACK (네, 받았습니다!)   │
   │ <────────────────────────────── │
   │                                 │
   │  ③ ACK (확인했습니다!)           │
   │ ──────────────────────────────> │
   │                                 │
   │         ESTABLISHED             │ ESTABLISHED
```

### 단계별 설명

**① SYN 세그먼트**
- 호스트 A가 초기 순서 번호와 함께 전송
- "연결 시작하자!" 신호

**② SYN + ACK 세그먼트**
- 호스트 B가 자신의 초기 순서 번호 + A의 확인 응답
- "네, 받았습니다. 연결 시작해요!"

**③ ACK 세그먼트**
- 호스트 A가 B의 응답 확인
- "확인했습니다!"
- 이후 **ESTABLISHED** 상태로 데이터 전송 시작

---

## 👋 TCP 연결 종료 - 4-Way Handshake

### 흐름도

```
호스트 A                          호스트 B
   │         ESTABLISHED             │ ESTABLISHED
   │                                 │
   │  ① FIN (연결 끊을게요)           │
   │ ──────────────────────────────> │
   │ FIN-WAIT-1                      │ CLOSE-WAIT
   │                                 │
   │  ② ACK (네, 알겠습니다)          │
   │ <────────────────────────────── │
   │ FIN-WAIT-2                      │
   │                                 │
   │  ③ FIN (저도 끊을게요)           │
   │ <────────────────────────────── │ LAST-ACK
   │ TIME-WAIT                       │
   │                                 │
   │  ④ ACK (네, 끊어요)              │
   │ ──────────────────────────────> │
   │                                 │
  CLOSED                            CLOSED
```

### 단계별 설명

**① FIN 세그먼트**
- 호스트 A: "연결 끊을게요"
- 상태: FIN-WAIT-1

**② ACK 세그먼트**
- 호스트 B: "알겠습니다"
- A는 FIN-WAIT-2, B는 CLOSE-WAIT 상태

**③ FIN 세그먼트**
- 호스트 B: "저도 끊을 준비 됐어요"
- B는 LAST-ACK 상태

**④ ACK 세그먼트**
- 호스트 A: "확인, 종료합니다"
- A는 TIME-WAIT 거쳐 CLOSED
- B는 바로 CLOSED

## 🔄 TCP 상태 (State)

### 연결 수립 상태

| 상태 | 설명 | 언제? |
|------|------|-------|
| **CLOSED** | 아무런 연결이 없는 상태 | 초기 상태 |
| **LISTEN** | 연결 요청 대기 중 | 서버가 클라이언트 기다림 |
| **SYN-SENT** | 액티브 오픈, SYN 전송 후 대기 | 클라이언트가 연결 시도 |
| **SYN-RECEIVED** | 패시브 오픈, SYN 받고 SYN+ACK 전송 | 서버가 응답 보낸 후 |
| **ESTABLISHED** | 연결 확립 완료 🎉 | 데이터 통신 가능 |

### 연결 종료 상태

| 상태 | 설명 | 언제? |
|------|------|-------|
| **FIN-WAIT-1** | 액티브 종료, FIN 전송 후 대기 | 먼저 종료 요청한 쪽 |
| **CLOSE-WAIT** | 종료 요청 받고 ACK 전송 | 종료 요청 받은 쪽 |
| **FIN-WAIT-2** | ACK 받고 상대방 FIN 대기 | 첫 ACK 받은 후 |
| **LAST-ACK** | FIN 전송 후 마지막 ACK 대기 | 나도 종료 준비 완료 |
| **TIME-WAIT** | 일정 시간 대기 후 종료 | 혹시 모를 패킷 대기 |
| **CLOSED** | 연결 완전 종료 | 끝! |

### 🤔 자주 헷갈리는 포인트

**액티브 오픈 vs 패시브 오픈**
- **액티브 오픈**: 먼저 연결/종료 요청하는 쪽 (클라이언트)
- **패시브 오픈**: 요청을 받아주는 쪽 (서버)

**TIME-WAIT 왜 필요해?**
- 마지막 ACK가 유실될 경우 재전송 대비
- 일정 시간 후 CLOSED 상태로 전환

### 🔍 실무 팁: netstat로 확인하기

```bash
$ netstat
```
- 현재 TCP 연결 상태를 확인할 수 있는 명령어
- macOS/Linux에서 사용 가능

## 🚀 UDP 데이터그램

### UDP 특징

**언제 쓰나?**
- 실시간 스트리밍 (영상, 음성)
- 온라인 게임
- DNS 조회
- 빠른 응답이 중요한 경우

**TCP와의 차이점:**

| 특징 | TCP | UDP |
|------|-----|-----|
| **순서 보장** | ✅ 순서 번호로 보장 | ❌ 보장 안 함 |
| **검사합** | ✅ 있음 | ⚠️ 있지만 선택적 |
| **재전송** | ✅ 손실 시 재전송 | ❌ 재전송 없음 |
| **연결** | 연결 지향 | 비연결형 |
| **속도** | 느림 | 빠름 |

### UDP 데이터그램 구조

```
┌──────────────┬──────────────┐
│   송신 포트   │   수신 포트   │
├──────────────┼──────────────┤
│     길이     │    체크섬     │
└──────────────┴──────────────┘
```

훨씬 간단함! → 오버헤드 적음 → 빠름

## 💡 핵심 요약

### TCP 핵심
1. **신뢰성**: 순서 보장, 재전송, 흐름 제어
2. **연결 수립**: 3-Way Handshake (SYN → SYN+ACK → ACK)
3. **연결 종료**: 4-Way Handshake (FIN → ACK → FIN → ACK)
4. **상태 관리**: CLOSED → LISTEN → ESTABLISHED → CLOSED
5. **주요 개념**:
    - 순서 번호: 데이터 구분
    - 확인 응답 번호: 수신 확인
    - 제어 비트: ACK, SYN, FIN

### UDP 핵심
1. **빠른 전송**: 오버헤드 최소화
2. **비연결형**: 연결 수립/종료 과정 없음
3. **신뢰성 없음**: 순서 보장 X, 재전송 X
4. **실시간 통신**: 스트리밍, 게임 등에 적합

### 언제 뭘 쓸까?

**TCP를 써야 할 때:**
- 웹 페이지 로딩 (HTTP/HTTPS)
- 파일 전송 (FTP)
- 이메일 (SMTP)
- 데이터 정확성이 중요한 경우

**UDP를 써야 할 때:**
- 실시간 영상/음성 통화
- 온라인 게임
- DNS 조회
- 약간의 패킷 손실은 괜찮은 경우

## 📝 복습 퀴즈

### Q1. TCP 3-Way Handshake의 올바른 순서는?

A. SYN → ACK → SYN+ACK  
B. SYN → SYN+ACK → ACK  
C. ACK → SYN → SYN+ACK  
D. SYN+ACK → SYN → ACK

**정답: B**

TCP 연결 수립은 (1) 클라이언트가 SYN 전송, (2) 서버가 SYN+ACK 응답, (3) 클라이언트가 ACK로 확인하는 순서입니다.

---

### Q2. TCP의 확인 응답 번호가 의미하는 것은?

A. 방금 받은 데이터의 순서 번호  
B. 다음에 받을 데이터의 순서 번호  
C. 전송한 데이터의 총 크기  
D. 수신 버퍼의 남은 공간

**정답: B**

확인 응답 번호는 "다음에 이 번호부터 보내주세요"라는 의미입니다. 예를 들어 순서 번호 100, 데이터 500바이트를 받았다면 확인 응답 번호는 600이 됩니다.

---

### Q3. UDP와 비교했을 때 TCP의 특징이 아닌 것은?

A. 순서 번호를 통한 데이터 순서 보장  
B. 손실된 패킷의 재전송  
C. 연결 수립 과정 없이 즉시 데이터 전송  
D. 흐름 제어 및 혼잡 제어

**정답: C**

연결 수립 과정 없이 즉시 데이터를 전송하는 것은 UDP의 특징입니다. TCP는 3-Way Handshake를 통해 연결을 먼저 수립합니다.

---

### Q4. TCP 연결 종료 시 TIME-WAIT 상태가 필요한 이유는?

A. 서버가 데이터를 모두 받을 때까지 대기  
B. 마지막 ACK가 유실될 경우를 대비  
C. 클라이언트가 추가 데이터를 보낼 수 있도록  
D. 서버의 처리 시간을 기다리기 위해

**정답: B**

TIME-WAIT 상태는 마지막 ACK 세그먼트가 유실되었을 경우, 상대방의 FIN 재전송에 대응하기 위해 일정 시간 대기하는 상태입니다.

---

### Q5. 다음 중 UDP를 사용하는 것이 적합한 서비스는?

A. 파일 다운로드  
B. 이메일 전송  
C. 실시간 영상 통화  
D. 웹 페이지 로딩

**정답: C**

실시간 영상 통화는 약간의 패킷 손실보다 빠른 전송이 중요하므로 UDP가 적합합니다. 파일 다운로드, 이메일, 웹 페이지는 데이터 정확성이 중요하므로 TCP를 사용합니다.
