# 07-1 안정성을 위한 기술

> 핵심 키워드: `가용성` `이중화` `다중화` `로드 밸런싱`

---

## 가용성 (Availability)

### 📌 정의
- 가용성 = **컴퓨터 시스템이 특정 기능을 실제로 수행할 수 있는 시간의 비율**
- "안정적인 시스템" = 가용성이 높은 시스템

### 📐 공식
```
가용성 = 업타임 / (업타임 + 다운타임)
```
- 업타임(uptime): 정상적인 사용이 가능한 시간
- 다운타임(downtime): 정상적인 사용이 불가능한 시간

### 🎯 고가용성 (High Availability, HA)
- 가용성이 높은 성질 → 고가용성 = HA
- 목표치: **99.999% 이상** (= 파이브 나인, Five Nines)

### 📊 가용성별 다운타임 표

| 가용성 | 1년간 다운타임 | 한 달간 다운타임 | 한 주간 다운타임 |
|--------|--------------|----------------|----------------|
| 90% (원 나인) | 36.53일 | 73.05시간 | 16.8시간 |
| 99% (투 나인) | 3.65일 | 7.31시간 | 1.68시간 |
| 99.9% (쓰리 나인) | 8.77시간 | 43.83분 | 10.08분 |
| 99.99% (포 나인) | 52.56분 | 4.38분 | 1.01분 |
| 99.999% (파이브 나인) | 5.26분 | 26.3초 | 6.05초 |
| 99.9999% (식스 나인) | 31.56초 | 2.63초 | 0.604초 |

### 💡 결함 감내 (Fault Tolerance)
- 다운타임 발생 원인을 모두 없애기는 현실적으로 불가능
- 핵심 = **문제가 발생해도 계속 기능할 수 있도록 설계**
- 가용성을 높이려면 결함을 감내하도록 서비스/인프라를 설계해야 함

---

## 이중화 (Redundancy)

### 📌 정의
- 이중화 = **무언가를 이중으로 두는 기술** → 결함 감내, 가용성 향상
- 쉽게 말해 "예비(백업)를 마련하는 방법"

### 🔍 이중화할 수 있는 대상
- 서버, 컴퓨터, 네트워크 인터페이스(NIC), 스위치, 물리적 장비
- 데이터베이스, 웹 서버 프로그램 등 소프트웨어도 이중화 가능

### ⚠️ SPOF (Single Point of Failure, 단일 장애점)
- 문제가 발생할 경우 **시스템 전체가 중단될 수 있는 대상**
- 예: 라우터가 고장나면 서비스 전체가 동작 안 됨
- 가용성을 높이려면 SPOF를 이중화해야 함

### 🔄 이중화 구성 방식

| 방식 | 설명 | 장점 | 단점 |
|------|------|------|------|
| 액티브/스탠바이 | 하나는 가동, 하나는 대기 | 안전한 구성 | 성능 향상 없음, 한 번에 하나만 가동 |
| 액티브/액티브 | 두 시스템 모두 가동 | 부하 분산 + 성능 향상 | 문제 발생 시 남은 서버에 부하 급증 |

> 💡 액티브 시스템에 문제 발생 → 스탠바이로 자동 전환 = **페일오버(Failover)**

## 다중화

### 📌 정의
- 다중화 = **무언가를 여러 개 두는 기술** (이중화의 확장 개념)
- 세 개 이상으로 구성 → 이중화보다 더욱 안정적인 운영

### 🔌 티밍(Teaming) & 본딩(Bonding)
- 여러 개의 NIC(네트워크 인터페이스)를 이중화/다중화
- 마치 하나의 인터페이스처럼 보이게 하는 기술
- 티밍: 주로 윈도우에서 사용
- 본딩: 주로 리눅스에서 사용
- 예: 1Gbps NIC 3개를 묶으면 → 3Gbps처럼 동작

---

## 로드 밸런싱 (Load Balancing)

### 📌 왜 필요한가?
- 서버를 다중화해도 **트래픽이 한 서버에만 몰리면** 가용성이 떨어짐
- 트래픽을 여러 서버에 고르게 분산시켜야 함

### 🔧 로드 밸런서 (Load Balancer)
- 로드 밸런싱은 **로드 밸런서**에 의해 수행됨
- L4 스위치, L7 스위치 같은 네트워크 장비로도 가능
- 소프트웨어로도 제공: **HAProxy**, **Envoy**, **Nginx** 등
- 클라이언트 ↔ 로드 밸런서 ↔ 다중화된 서버들

> L4 스위치: IP 주소, 포트 번호 등 전송 계층 정보 기반으로 로드 밸런싱  
> L7 스위치: URL, HTTP 메시지, 쿠키 등 응용 계층 정보로 로드 밸런싱

### 📋 로드 밸런싱 알고리즘

| 알고리즘 | 설명 |
|---------|------|
| 라운드 로빈 (Round Robin) | 서버를 순서대로 돌아가며 선택 |
| 최소 연결 (Least Connection) | 연결이 가장 적은 서버 우선 선택 |
| 가중치 라운드 로빈 | 가중치가 높은 서버에 더 많은 요청 |
| 가중치 최소 연결 | 가중치 + 연결 수 고려 |
| 해시(Hash) | 해시 자료구조 이용 |
| 응답시간 기반 | 응답 시간이 가장 빠른 서버 선택 |

### 🩺 헬스 체크 (Health Check)
- 로드 밸런서가 주기적으로 서버 상태 검사
- 문제 있는 서버로는 요청을 전달하지 않음
- HTTP, ICMP 등 다양한 프로토콜 활용 가능
- 서버끼리 주기적으로 **하트비트(Heartbeat)** 메시지를 교환하는 방식도 있음

## 포워드 프록시 & 리버스 프록시

### 📌 오리진 서버 (Origin Server)
- 클라이언트가 최종적으로 메시지를 주고받는 대상
- 클라이언트에게 관련된 응답을 보낼 수 있는 HTTP 서버

### 🔀 프록시 (Proxy) = 포워드 프록시
- 정의: **클라이언트가 선택한 메시지 전달 대리자**
- 클라이언트 가까이 위치
- 주요 기능: 캐시 저장, 클라이언트 암호화 및 접근 제어

```
[클라이언트] → [프록시] → [인터넷] → [오리진 서버들]
```

### 🔀 게이트웨이 = 리버스 프록시
- 정의: **아웃바운드 연결에 대해 오리진 서버 역할을 하지만, 수신된 요청을 다른 인바운드 서버로 전달하는 중개자**
- 오리진 서버 가까이 위치
- 외부에서 보면 오리진 서버처럼 보임
- 주요 기능: 캐시 저장, 로드 밸런서로 동작 가능

```
[클라이언트] → [인터넷] → [게이트웨이(리버스 프록시)] → [오리진 서버들]
```

> 💡 비유: 오리진 서버들의 네트워크 = "대저택"  
> 프록시 = 클라이언트를 대신해 대저택에 심부름 가는 심부름꾼  
> 게이트웨이 = 대저택을 지키는 경비원

# 07-2 안전성을 위한 기술

> 핵심 키워드: `대칭 키 암호화` `공개 키 암호화` `공개 키 인증서` `디지털 서명` `SSL` `TLS` `HTTPS` `TLS 핸드셰이크`

---

## 암호화와 복호화

### 📌 정의
- **암호화(Encryption)**: 원문 데이터를 알아볼 수 없는 형태로 변환
- **복호화(Decryption)**: 암호화된 데이터를 원문으로 되돌리는 과정
- 두 가지 목적: 안전한 데이터 송수신 + 인증 기반의 검증

### 🔑 키 (Key)
- 자물쇠의 영문 표현이지만, 보안에서의 키는 무작위해 보이는 문자열
- 키와 원문을 수학적 연산 → 암호문 생성 (= 암호화 알고리즘)
- 복호화하면 원문 메시지를 얻을 수 있음

---

## 대칭 키 암호화

### 📌 정의
- 암호화와 복호화에 **동일한 키**를 사용하는 방식
- 두 호스트가 같은 키로 암호화 & 복호화 수행 (= "대칭" 키)

### ⚠️ 단점
- 상대방에게 키를 **안전하게 전달하기 어려움**
- 키가 유출되면 모든 암호화 통신이 무너짐

### ✅ 장점
- 적은 부하로 암호화 & 복호화를 빠르게 수행 가능

---

## 공개 키 암호화 (비대칭 키)

### 📌 정의
- 암호화와 복호화에 **다른 키**를 사용하는 방식 (= 비대칭 키 암호화)
- 키 쌍으로 구성:
    - **공개 키(Public Key)**: 누구에게나 공개해도 무방
    - **개인 키(Private Key)**: 절대 유출되면 안 됨

### 🔐 동작 원리
```
공개 키로 암호화 → 개인 키로만 복호화 가능
개인 키로 암호화 → 공개 키로만 복호화 가능
```

### 📮 예시: A → B로 안전하게 메시지 전송
1. A가 B의 공개 키를 요청 → B가 공개 키 전달
2. A는 B의 공개 키로 메시지를 암호화 → 암호문 전송
3. B는 자신의 개인 키로 복호화 → "안녕, 나는 A야" 확인

### ⚠️ 단점
- 대칭 키 암호화보다 암호화/복호화에 시간과 부하가 많이 필요

### 💡 혼합 사용: 세션 키(Session Key)
- 실무에서는 두 방식을 함께 사용
- 공개 키로 대칭 키(= 세션 키)를 암호화해서 전달
- 이후 세션 키로 빠른 암호화/복호화 수행

---

## 인증서와 디지털 서명

### 📌 공개 키 인증서 (Public Key Certificate)
- 공개 키와 공개 키의 유효성을 입증하기 위한 전자 문서
- 서버로부터 받은 공개 키가 진짜인지 확인하기 위해 필요
- 인증서에는 공개 키, 유효 기간, 서버 정보 등이 포함됨

### 🏛️ CA (Certification Authority, 인증 기관)
- 인증서를 발급, 검증, 저장하는 공인 기관
- 대표적 CA: **IdenTrust**, **DigiCert**, **GlobalSign**
- CA가 발급한 인증서에는 **서명 값(Signature)** 포함

### ✍️ 디지털 서명 (Digital Signature)
- 개인 키로 암호화한 메시지를 공개 키로 복호화함으로써 신원을 증명하는 절차

**서명 만드는 과정:**
```
인증서 내용 → [해시 함수] → 해시 값(지문) → [CA의 개인 키로 암호화] → 서명 값
```

**검증 과정:**
```
① 전달받은 서명 값 → [CA의 공개 키로 복호화] → 해시 값
② 인증서 내용 → [해시 함수] → 해시 값
③ ①과 ② 비교 → 일치하면 인증서 신뢰
```

### 🔢 해시 함수 & 해시 값
- 임의 길이의 데이터를 고정 길이 데이터로 변환하는 함수
- 입력 데이터가 조금만 달라도 완전히 다른 결과가 나옴
- 주요 해시 함수: MD5, SHA-1, SHA-256, SHA-384, SHA-512
- 활용: 데이터가 전송 도중 변조되었는지 검사할 때 사용

## HTTPS: SSL과 TLS

### 📌 SSL vs TLS
| 항목 | 내용 |
|------|------|
| SSL | Secure Sockets Layer — 초기 프로토콜 (현재 SSL 1.0~3.0 모두 폐지) |
| TLS | Transport Layer Security — SSL을 계승한 프로토콜 |
| 순서 | SSL 2.0 → SSL 3.0 → TLS 1.0 → TLS 1.1 → TLS 1.2 → TLS 1.3 |

> 현재 주로 사용: **TLS 1.3**

### 🌐 HTTPS
- HTTP 메시지의 SSL/TLS를 사용하는 프로토콜
- 브라우저 주소창의 자물쇠 아이콘 = HTTPS 사용 중

---

## TLS 핸드셰이크

> HTTPS 메시지는 다음 3단계를 거쳐 송수신됨

### 1️⃣ TCP 쓰리 웨이 핸드셰이크
- SYN → SYN+ACK → ACK (4장 내용 참고)

### 2️⃣ TLS 핸드셰이크
**핵심 2가지 목적:**
1. 암호화 통신을 위한 키 교환
2. 인증서 송수신과 검증

**주요 메시지 흐름 (TLS 1.3 기준):**

```
[클라이언트]                        [서버]
      |                                |
      |-------- ClientHello --------→ |
      |         (key_share 포함)       |
      |                                |
      |← ServerHello                  |
      |← EncryptedExtensions          |
      |← Certificate                  |
      |← CertificateVerify            |
      |← Finished -------------------|
      |                                |
      |-------- Finished ----------→  |
      |                                |
      |← 암호화된 Application Data ----|
      |--- 암호화된 Application Data →|
```

**각 메시지 설명:**

| 메시지 | 방향 | 내용 |
|--------|------|------|
| ClientHello | C→S | 지원하는 TLS 버전, 암호 스위트, 클라이언트 난수 등 |
| ServerHello | S→C | 선택된 TLS 버전, 암호 스위트, 서버 난수 등 |
| Certificate | S→C | 서버의 인증서 전달 |
| CertificateVerify | S→C | 디지털 서명 (검증용) |
| Finished | 양방향 | 핸드셰이크 마지막 메시지 |

### 🔐 암호 스위트 (Cipher Suite)
- 암호화 방식과 해시 함수를 담은 정보
- 예시:
    - `TLS_AES_128_GCM_SHA256`
    - `TLS_AES_256_GCM_SHA384`
    - `TLS_CHACHA20_POLY1305_SHA256`

### 3️⃣ 암호화된 메시지 송수신
- TLS 핸드셰이크를 통해 얻은 키로 이후 모든 데이터 암호화
- TLS 1.3에서는 Finished 메시지와 함께 Application Data 전송 가능

**Q1. 가용성을 나타내는 공식으로 올바른 것은?**

A. 업타임 / 다운타임  
B. 업타임 / (업타임 + 다운타임)  
C. 다운타임 / (업타임 + 다운타임)  
D. 업타임 × 다운타임  
E. (업타임 + 다운타임) / 업타임

정답: B  
해설: 가용성은 전체 사용 시간 중 정상적으로 동작한 시간의 비율이다. 즉, 업타임을 전체 시간(업타임 + 다운타임)으로 나눈 값이다.

**Q2. SPOF(Single Point of Failure)에 대한 설명으로 올바른 것은?**

A. 가용성이 100%인 시스템을 의미한다  
B. 문제 발생 시 시스템 전체가 중단될 수 있는 단일 대상이다  
C. 이중화가 완료된 장비를 부르는 이름이다  
D. 로드 밸런서의 알고리즘 중 하나이다  
E. 네트워크 인터페이스 카드의 약자이다

정답: B  
해설: SPOF는 해당 지점에서 문제가 발생하면 전체 시스템이 멈출 수 있는 취약한 단일 지점을 말한다. 가용성을 높이려면 이 SPOF를 이중화해야 한다.

**Q3. 다음 중 로드 밸런싱 알고리즘이 아닌 것은?**

A. 라운드 로빈  
B. 최소 연결  
C. 페일오버  
D. 가중치 라운드 로빈  
E. 해시

정답: C  
해설: 페일오버(Failover)는 액티브 시스템에 문제가 발생했을 때 스탠바이 시스템으로 자동 전환하는 메커니즘이다. 로드 밸런싱 알고리즘이 아니라 이중화 구성에서 사용하는 개념이다.

**Q4. 포워드 프록시와 리버스 프록시(게이트웨이)에 대한 설명 중 옳은 것은?**

A. 포워드 프록시는 오리진 서버 가까이 위치한다  
B. 리버스 프록시는 클라이언트가 선택하는 대리자이다  
C. 포워드 프록시는 클라이언트를 대신해 서버에 요청을 보내는 역할을 한다  
D. 리버스 프록시는 로드 밸런서로 동작할 수 없다  
E. 두 프록시 모두 캐시를 저장하지 못한다

정답: C  
해설: 포워드 프록시(프록시)는 클라이언트가 선택한 대리자로, 클라이언트 가까이에 위치해 클라이언트를 대신하여 서버에 요청을 보낸다. 리버스 프록시(게이트웨이)는 서버 가까이에 위치하며 로드 밸런서로도 동작 가능하고 캐시도 저장할 수 있다.

**Q5. 대칭 키 암호화의 가장 큰 단점은?**

A. 암호화와 복호화 속도가 너무 느리다  
B. 키를 상대방에게 안전하게 전달하기 어렵다  
C. 한 번만 사용할 수 있다  
D. 인터넷에서 사용이 불가능하다  
E. 반드시 인증 기관(CA)이 필요하다

정답: B  
해설: 대칭 키 암호화는 암호화/복호화에 같은 키를 사용하므로, 이 키를 상대방에게 안전하게 전달하는 방법이 문제가 된다. 키가 도중에 탈취되면 모든 암호화가 무의미해진다.

**Q6. 공개 키 암호화에서 A가 B에게 메시지를 안전하게 보내려 할 때 올바른 절차는?**

A. A의 개인 키로 암호화 → B의 공개 키로 복호화  
B. B의 공개 키로 암호화 → B의 개인 키로 복호화  
C. A의 공개 키로 암호화 → A의 개인 키로 복호화  
D. B의 개인 키로 암호화 → A의 공개 키로 복호화  
E. 공개 키와 개인 키 중 아무거나 선택해서 사용 가능

정답: B  
해설: 공개 키 암호화에서 B에게만 읽힐 수 있는 메시지를 보내려면 B의 공개 키로 암호화해야 한다. 그러면 B만 가지고 있는 개인 키로만 복호화가 가능하다.

**Q7. 디지털 서명(Digital Signature)에 대한 설명으로 옳은 것은?**

A. 공개 키로 암호화하고 공개 키로 복호화하는 과정이다  
B. 개인 키로 암호화한 메시지를 공개 키로 복호화하여 신원을 증명하는 과정이다  
C. 인증 기관 없이도 누구나 자체적으로 만들 수 있는 인증서다  
D. 해시 함수를 사용하지 않는다  
E. TLS 핸드셰이크 이후에만 사용 가능하다

정답: B  
해설: 디지털 서명은 CA의 개인 키로 인증서의 해시 값을 암호화하여 서명 값을 만든다. 클라이언트는 CA의 공개 키로 이 서명 값을 복호화하여 인증서의 유효성을 검증한다. 개인 키로만 만들 수 있고 공개 키로 누구나 검증할 수 있다는 특성이 핵심이다.

**Q8. TLS 핸드셰이크의 핵심 목적 2가지를 올바르게 고른 것은?**

A. 데이터 전송 속도 향상 + 서버 다중화  
B. 암호화 통신을 위한 키 교환 + 인증서 송수신 및 검증  
C. IP 주소 할당 + 포트 번호 협상  
D. 로드 밸런싱 알고리즘 결정 + 세션 종료 처리  
E. DNS 조회 + ARP 요청

정답: B  
해설: TLS 핸드셰이크의 두 가지 핵심 목적은 (1) 이후 암호화 통신에 사용할 키를 교환하는 것, (2) 서버의 인증서를 주고받고 검증하는 것이다. 이 과정을 통해 안전한 HTTPS 통신이 가능해진다.
